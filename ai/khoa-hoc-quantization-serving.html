Quantization & Serving LLM — End-to-End

16 chương theo 4 cấp độ. Ép mô hình nặng hàng chục GB chạy mượt trên GPU eo hẹp (RTX 3090/4090 24GB). Quantization (INT4 — GPTQ/AWQ/GGUF) nén model 4×; serving (vLLM/TGI) phục vụ hàng nghìn request. End-to-end: tải FP16 → lượng tử → serve → benchmark throughput/TTFT/VRAM. Mỗi chương có code, bài tập tự chấm, quiz, flashcard.

L0 · Nền tảng

Chương 1 Vì sao cần quantization

GPU consumer eo hẹp — model thì khổng lồ.

Model 7B FP16 = ~14GB chỉ trọng số; 70B = ~140GB — vượt xa GPU phổ thông (24GB). Quantization nén trọng số từ FP16 (16-bit) xuống INT4 (4-bit) → giảm 4× → 7B chỉ ~4GB, chạy được trên GPU consumer.

FP16INT8INT4
Bit/param1684
Model 7B~14 GB~7 GB~4 GB
Chất lượng100%~99%~96–98%
Chạy trên RTX 3090 (24GB)?Khó (hết cho KV cache)ĐượcDư dật + batch được
INT4 là sweet spot Nén 4× với chỉ 2–4% mất chất lượng — đủ cho 99% use case serving. Lõi bài toán: memory-bound (LLM inference bị giới hạn bởi băng thông VRAM, không phải tính toán) → nén trọng số tăng tốc luôn.
📝 Quiz nhanh
1. INT4 quantization giảm VRAM bao nhiêu lần so FP16?
✅ FP16=16 bit/param, INT4=4 bit → giảm đúng 4×. INT8 giảm 2×.

Chương 2 FP16 vs INT8 vs INT4

3 mức nén — 3 đánh đổi.
  • FP16/BF16: huấn luyện gốc, độ chính xác cao. BF16 dùng cho train (tràn số tốt hơn).
  • INT8: nén 2×, mất rất ít chất lượng (~1%). Dễ nhất, hỗ trợ rộng.
  • INT4: nén 4×, mất vài %, đủ cho hầu hết use case. Sweet spot.
Lượng tử trọng số vs activation Đa số quantization chỉ nén trọng số (weights), giữ activation ở độ cao (FP16) để giữ chất lượng. AWQ/GPTQ đều vậy. QAT mới nén cả activation.

Chương 3 Các phương pháp quantization

PTQ vs QAT; 3 định dạng chính.
Phương phápÝ tưởngKhi nào

PTQ là mặc định AWQ/GPTQ (PTQ) đủ tốt cho serving production. QAT chỉ khi bạn fine-tune riêng & cần vắt kiệt chất lượng — tốn GPU & data.

Chương 6 AutoAWQ — lượng tử INT4

AWQ bảo vệ trọng số quan trọng.
python · AWQ●
from awq import AutoAWQForCausalLM

model = AutoAWQForCausalLM.from_pretrained("meta-llama/Meta-Llama-3-8B")
model.quantize("./calib-data", quant_config={
    "zero_point": False, "w_bit": 4, "q_group_size": 128
})
model.save_quantized("./llama3-8b-awq")   # ~4 GB
Vì sao AWQ > GPTQ ở INT4 AWQ (Activation-aware Weight Quantization) xem xét activation để bảo vệ trọng số "quan trọng" (salient) khỏi bị nén sát → ít mất chất lượng hơn GPTQ ở INT4. Lựa chọn ưu tiên ngày nay.
✍️ Bài tập 3 — Gọi quantize
Gọi model.quantize("./calib-data", quant_config={"w_bit": 4, "q_group_size": 128}).
Xem lời giải
model.quantize("./calib-data", quant_config={"w_bit": 4, "q_group_size": 128})

Chương 7 AutoGPTQ (alternative)

Cũ hơn AWQ, được hỗ trợ rộng.

GPTQ dùng xấp xỉ Gauss-Newton, lượng tử từng lớp một dựa trên dữ liệu calibration. Cũ hơn AWQ, được hỗ trợ rộng hơn (nhiều engine). Khi AWQ không có cho model bạn cần → dùng GPTQ.

AWQ vs GPTQ — chọn nào? Ưu tiên AWQ (chất lượng INT4 tốt hơn). Nếu engine của bạn chỉ hỗ trợ GPTQ, hoặc model chỉ có bản GPTQ trên Hub → dùng GPTQ. Khác biệt nhỏ trong thực tế.

Chương 10 PagedAttention — vì sao vLLM nhanh

Bí mật: quản lý KV cache như virtual memory.

vLLM dùng PagedAttention: quản lý KV cache như virtual memory (paging) — không phân mảnh, batch được nhiều request hơn cùng lúc. Throughput cao hơn HF Transformers 10–20× ở cùng phần cứng.

Continuous batching vLLM còn dùng continuous batching: request mới vào ngay khi request cũ xong (không đợi cả batch). Tận dụng GPU tối đa — đây là vì sao production dùng vLLM/TGI chứ không phải model.generate() trực tiếp.
📝 Quiz
1. PagedAttention cải thiện gì?
✅ PagedAttention = paging cho KV cache → throughput 10-20× so generate thường.

Chương 11 OpenAI-compatible API

Không lock-in — đổi base_url là chạy.

vLLM/TGI/llama-cpp-python đều expose API giống OpenAI → code sẵn của bạn (langchain, openai SDK) chỉ đổi base_url là chạy. Chuyển giữa local Llama ↔ OpenAI GPT mà không sửa logic.

Streaming Mọi engine hỗ trợ stream=True (SSE) — trả token từng chữ. UX "đang gõ" như ChatGPT. Bật bằng stream=True trong client.

Chương 13 Stress test

Đo throughput & TTFT.
python · async benchmark●
import asyncio, httpx, time

async def fire(c, q):
    t0 = time.time()
    r = await c.post("http://localhost:8000/v1/completions",
        json={"model":"x", "prompt":q, "max_tokens":100})
    dt = time.time() - t0
    toks = r.json()["usage"]["completion_tokens"]
    return toks/dt   # tokens/giây

async def main():
    async with httpx.AsyncClient() as c:
        results = await asyncio.gather(*[fire(c,"Viết email") for _ in range(100)])
    print("avg tokens/s:", sum(results)/len(results))
✍️ Bài tập 5 — Tính tokens/giây
Viết hàm throughput(n_tokens, seconds) trả n_tokens / seconds.
Xem lời giải
def throughput(n_tokens, seconds):
    return n_tokens / seconds

Chương 14 Peak VRAM & tránh OOM

3 nút khi hết VRAM.
  • Đo nvidia-smi trong lúc serve — theo dõi peak.
  • Batch lớn → VRAM cao hơn nhưng throughput tốt hơn (đổi theo traffic).
  • OOM → giảm max_model_len (context ngắn), giảm gpu_memory_utilization (vd 0.8), dùng INT4.
KV cache là kẻ ngốn #1 Khi serve, VRAM không chỉ cho trọng số mà còn cho KV cache của mọi request đang xử lý. Request dài + nhiều user = KV cache phình to → OOM. Giảm max_model_len hoặc dùng quantize KV cache (vLLM hỗ trợ --kv-cache-dtype fp8).

Chương 16 Dự án: serve Llama-3-8B trên RTX 3090

Ráp toàn bộ — đo trước/sau.
  1. Tải FP16: load + đo VRAM (~15GB — vừa 24GB nhưng không dư cho batch).
  2. AWQ INT4: lượng tử → ~4GB.
  3. vLLM serve: vllm serve --quantization awq.
  4. Stress test: 100 request đồng thời, đo throughput + TTFT.
  5. So sánh: FP16 (chỉ 1-2 request) vs INT4 (batch 10+ request).
  6. Báo cáo: throughput (tokens/s), TTFT (ms), peak VRAM.
Hoàn thành khóa học 🎉 Bạn có thể ép LLM lớn chạy trên GPU consumer & phục vụ production. Tiếp theo: kết hợp fine-tune ở PEFT/LoRA (serve nhiều adapter), RAG ở LangChain + Hybrid Search.
