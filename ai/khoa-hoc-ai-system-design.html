AI System Design — Hệ thống AI triệu user

16 chương theo 4 cấp độ. Định dạng phỏng vấn Senior ở công ty công nghệ lớn: thiết kế hệ thống AI phục vụ triệu user. Capacity estimation (DAU→QPS→storage), trade-off (SQL/NoSQL/Vector DB, cache, queue), scale (sharding/LB/rate limit) — qua 3 case study: Recommender, ChatGPT clone, AI Search. Mỗi chương có bài tập tự chấm, quiz, flashcard.

L0 · Khung System Design

Chương 1 System Design AI là gì

Khác ML truyền thống — thêm GPU cost, model serving, context window.

Khác ML system design truyền thống, AI system design phải lo thêm: GPU cost (inference tốn tiền mỗi request), model serving (vLLM, batching, quantize), context window (lưu lịch sử chat), vector DB (RAG/search). Mục tiêu phỏng vấn: không có đáp án "đúng" — bạn cần justify trade-off.

Interviewer muốn thấy gì Khả năng (1) clarify yêu cầu trước khi nhảy vào giải pháp, (2) estimate quy mô bằng số, (3) vẽ kiến trúc rõ ràng, (4) defend trade-off dưới câu hỏi "vì sao chọn X không Y". Không phải ra thiết kế hoàn hảo — mà là tư duy có cấu trúc.
📝 Quiz nhanh
1. Mục tiêu chính của vòng phỏng vấn System Design?
✅ Interviewer đánh giá quá trình tư duy — clarify, estimate, trade-off — hơn kết quả.

Chương 2 Khung phỏng vấn 4 bước

Bản đồ cho 45-60 phút.
  1. Clarify (5-10') — functional & non-functional requirements. Hỏi interviewer.
  2. Capacity (5') — DAU, QPS, storage, bandwidth (back-of-envelope math).
  3. High-level Design (15-20') — vẽ diagram: client → LB → service → DB/cache/queue.
  4. Deep Dive (15-20') — focus 1-2 bottleneck, defend trade-off.
Quản lý thời gian Lỗi phổ biến #1: mắc ở bước clarify/quá sa vào detail sớm. Bám khung 4 bước, interviewer sẽ guide. Luôn state assumptions rõ ràng để interviewer follow.

Chương 4 Capacity Estimation

Back-of-envelope math — đo bằng số trước khi vẽ.
tính toán●
# Cho: 1M DAU, 10 msg/user/day, mỗi msg 2KB
requests_per_day = 1_000_000 * 10           # 10M
qps             = 10_000_000 / 86400        # ~116 req/s
peak_qps        = qps * 3                    # ~350 (3× peak)
storage_day     = 10_000_000 * 2 * 1024      # bytes → ~20 GB/day
storage_year    = storage_day * 365          # ~7.3 TB/năm
✍️ Bài tập 1 — Tính QPS
Viết công thức QPS = (DAU × requests_per_user_per_day) / 86400. Dùng biến dau và req.
Xem lời giải
qps = dau * req / 86400
L1 · Thành phần & Trade-off

Chương 5 Database choice

Đúng tool cho đúng việc.
LoạiKhi nàoVí dụ AI

NoSQL (Cassandra)Linh hoạt schema, scale ngang, write-heavyLịch sử chat (triệu dòng)
Vector DB (Qdrant)Tìm ngữ nghĩa (embedding)RAG, AI search

Đừng cố 1 DB cho tất cả Hệ thống lớn luôn dùng nhiều loại: SQL cho billing, NoSQL cho chat log, vector DB cho RAG, Redis cho cache. Polyglot persistence.

Chương 6 Caching

Đòn bẩy #1 giảm load & cost.
  • Redis/Memcached: cache kết quả truy vấn / nội dung nóng.
  • Semantic caching (LLM): cache theo ý nghĩa câu — query tương tự → trả đáp án cũ. Giảm 30-60% LLM call.
  • Write-through vs write-around: trade-off nhất quán vs tốc độ.
Semantic cache cho LLM Embedding query → tìm trong cache query cũ nào cosine similarity > 0.95 → trả đáp án cũ. Tiết kiệm GPU/API cost khổng lồ cho FAQ-like traffic. Cẩn thận invalidation khi dữ liệu đổi.

Chương 7 Message Queue

Decouple — tránh timeout, chịu tải.

Kafka/RabbitMQ tách request khỏi xử lý: client gửi → queue → worker xử lý async → client poll kết quả. Dùng cho: batch job, train offline, email gửi sau, tác vụ LLM lâu (> 10s).

✍️ Bài tập 2 — Vì sao dùng queue?
Nêu 2 lý do đẩy tác vụ LLM lâu (hàng chục giây) vào queue thay vì xử lý đồng bộ (gợi ý: timeout, async, retry...).
Xem lời giải
(1) Tránh client timeout khi tác vụ lâu. (2) Chịu tải spike + retry được khi fail. (3) Worker scale ngang độc lập với API.

Chương 8 Scale: Sharding, LB, Rate Limiting

Từ 1 server lên nghìn.
  • Sharding: chia DB theo key (user_id) → mỗi shard 1 phần dữ liệu. Scale ngang.
  • Load Balancer: L4 (TCP) hoặc L7 (HTTP, smart routing) — phân tải nhiều instance.
  • Rate Limiting: Token Bucket — chống bot/DDoS sập API. Mỗi user N request/phút.
📝 Quiz
1. Sharding giải quyết vấn đề gì?
✅ Sharding = chia DB theo key (user_id, region) → mỗi shard 1 phần → scale ngang.
L2 · Case Study AI

Chương 9 Case Study: Recommender System

Two-tower — chuẩn industry cho triệu item.

Two-tower model chia thành 3 giai đoạn:

  1. Retrieval: từ triệu item → top-1000 candidate (embedding similarity, fast).
  2. Ranking: model chi tiết xếp lại top-1000 → top-50 (nhiều feature).
  3. Re-ranking: filter logic kinh doanh (đa dạng, mới, không trùng).
Near-line vs Offline Offline: train model nightly trên cluster Spark. Near-line: feature realtime (click 5 phút qua) qua Redis — cập nhật gợi ý phản ánh hành vi mới. Cả hai kết hợp.
✍️ Bài tập 3 — 3 giai đoạn recommender
Liệt kê 3 giai đoạn pipeline recommender (gợi ý: retrieval, ranking, re-ranking).
Xem lời giải
(1) Retrieval — triệu item → top-1000. (2) Ranking — top-1000 → top-50 bằng model chi tiết. (3) Re-ranking — filter logic kinh doanh.

Chương 10 Case Study: ChatGPT Clone

Streaming + context storage + model serving.
  • Streaming: SSE (đơn giản, 1 chiều server→client) hoặc WebSocket (2 chiều). Chat thường SSE đủ.
  • Context window: lưu lịch sử chat ở Cassandra/DynamoDB, lazy-load N tin gần nhất khi cần — không load toàn bộ mỗi request.
  • Model serving: vLLM multi-tenant, PagedAttention, batch user. Quantize INT4 nếu GPU eo hẹp.
SSE vs WebSocket Chat LLM: SSE đơn giản hơn (HTTP, tự reconnect, cache-friendly), đủ vì chỉ cần server→client. WebSocket khi cần 2 chiều (voice, realtime collab). Đừng over-engineer.

Chương 11 Case Study: AI Search Engine

Crawling → indexing → vector sharding.

Pipeline: crawling (thu thập web) → indexing (inverted index + vector) → vector DB sharding (HNSW/IVF). Trade-off Recall vs Latency:

HNSWIVF
Tốc độNhanh (đồ thị)Trung bình
RAMNhiều (giữ đồ thị trong RAM)Ít hơn
RecallCaoThấp hơn (đổi theo nprobe)
✍️ Bài tập 4 — HNSW vs IVF
Nêu đánh đổi chính giữa HNSW và IVF (gợi ý: RAM, latency, recall).
Xem lời giải
HNSW: nhanh + recall cao nhưng tốn nhiều RAM (giữ đồ thị). IVF: ít RAM hơn, đổi lại latency/recall thấp hơn (điều chỉnh nprobe).

Chương 12 ML: serving, A/B, feature store

Đưa model ra production an toàn.
  • Canary deploy: 5% traffic model mới trước → giám sát metric → mở rộng/rollback.
  • A/B test: so model mới vs cũ trên metric (retention, CTR, latency). Ý nghĩa thống kê.
  • Feature store: đảm bảo feature train & serve nhất quán (training-serving skew) — nguồn bug thầm lặng.
Training-serving skew Model train với feature tính 1 cách, nhưng serve tính khác (vd train dùng data batch, serve realtime thiếu) → hiệu năng production tụt. Feature store (Feast, Tecton) giải quyết.
L3 · Thực chiến

Chương 13 High-level Design: vẽ & communicate

Diagram rõ ràng — hơn 1000 chữ.

Vẽ theo layer: client → CDN/LB → API gateway → service layer → (DB / cache / queue / model server). Mỗi box ghi rõ trách nhiệm. Communicate suy nghĩ thành tiếng — interviewer cần thấy quá trình.

Mẹo vẽ Bắt đầu đơn giản (client → service → DB), rồi thêm khi interviewer hỏi ("cache ở đâu?", "queue?"). Đừng vẽ hết 20 component ngay — rối và mất thời gian.

Chương 14 Bottleneck deep dive

Focus 1-2 điểm — chiều sâu hơn bề rộng.

Interviewer sẽ hỏi "chỗ này có vấn đề gì?" — chọn 1-2 bottleneck & giải:

  • Độ trễ inference cao → batch + quantize (INT4) + cache + route model rẻ cho query đơn giản.
  • Vector search chậm → sharding + HNSW + rerank 2 giai đoạn.
  • LLM cost cao → semantic cache + route model + prompt ngắn gọn.
  • Hot key trong DB → consistent hashing + replica.
Đừng cố cover tất cả 45 phút không đủ cho mọi detail. Chọn 1-2 bottleneck quan trọng nhất (thường interviewer hint) & giải sâu. Chiều sâu tại 1 điểm > sơ sài ở 10 điểm.

Chương 15 Mẹo phỏng vấn Senior

Phân biệt ứng viên Senior với Mid.
  • Clarify trước khi vẽ — 5 phút hỏi requirements đáng giá. Đừng nhảy vào giải pháp.
  • State assumptions rõ ràng ("giả sử 1M DAU") & xin xác nhận.
  • Back-of-envelope math — cho thấy tư duy quy mô, không đoán mò.
  • Trade-off thay vì "đáp án đúng" — so sánh 2 lựa chọn, nói khi nào chọn cái nào.
  • Đừng im lặng — nghĩ thành tiếng, interviewer không đọc được suy nghĩ.
  • Recognize hint — interviewer gợi ý ("thế nếu user gõ 1000 msg/phút?") → đó là hướng deep dive.

Chương 16 Dự án: mock interview

Ráp toàn bộ — luyện thực sự.

Chọn 1 bài (vd "thiết kế chatbot CSKH 1M user"), thực hành 4 bước:

  1. Clarify: trả lời dựa tài liệu? đa ngữ? peak traffic?
  2. Capacity: 1M DAU × 10 msg × 2KB → QPS, storage/năm.
  3. High-level: client → LB → API → RAG (vector DB + hybrid search) → LLM (vLLM) → stream SSE. Cassandra cho chat log, Redis cache.
  4. Deep dive: streaming + semantic cache + quantize cho GPU cost.

Viết solution doc 2 trang. Mock với bạn/mentor 45'. Quay video & tự review.

✍️ Bài tập 5 — Tính storage/năm
Chatbot 1M DAU, mỗi user 10 msg/day, mỗi msg 2KB. Tính storage_year bytes (gợi ý: dau * msg * size * 365).
Xem lời giải
storage_year = 1_000_000 * 10 * 2 * 1024 * 365   # ~7.3 TB
Hoàn thành toàn bộ roadmap 🎉 Bạn đã đi hết 6 mục bổ sung — từ MCP/DSPy (framework mới) qua Hybrid/RAGAS (RAG nâng cao) đến Quantization (serving) & System Design (Senior). Đây là mảnh cuối ghép bạn từ người dùng API thành kỹ sư AI thực chiến. Luyện mock interview thường xuyên — System Design là kỹ năng cũ hơn theo năm.
