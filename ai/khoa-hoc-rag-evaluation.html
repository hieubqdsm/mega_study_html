Đánh Giá RAG Định Lượng — RAGAS & TruLens

16 chương theo 4 cấp độ. "Chấm điểm" RAG bằng số liệu thay cảm tính. RAGAS/TruLens đo theo 4 trục: Faithfulness (không ảo giác), Answer Relevancy (trúng câu hỏi), Context Precision/Recall (tìm đúng tài liệu). So sánh khách quan giữa các config RAG. Mỗi chương có code, bài tập tự chấm, quiz, flashcard.

📖 16 chương · 4 cấp độ ✍️ Bài tập tự chấm 🔧 RAG Eval Builder 📊 RAGAS · TruLens
Chuẩn bị Cài pip install ragas. Cần LLM làm giám khảo (OpenAI GPT-4o-mini) hoặc local. Học RAG ở LangChain / LlamaIndex, retrieval ở Hybrid Search trước. Bài tập tự chấm offline.
L0 · Nền tảng

Chương 1 Vì sao cần đánh giá RAG định lượng

"Có vẻ ổn" không đủ — cần số liệu tái lập được.

"AI trả lời có vẻ ổn" không đủ. Khi đổi chunk size, đổi model, thêm rerank — bạn cần biết cải thiện hay làm hỏng. Đánh giá bằng cảm tính = không tái lập được, không thuyết phục được ai. Đánh giá định lượng = unit test cho RAG: chạy lại trên cùng eval set, so sánh số, quyết định dựa dữ liệu.

Không đo = đoán mò Nhiều team RAG sống trong "vùng tối": không biết chất lượng thật, đến khi user phàn nàn mới phát hiện. Eval định lượng biến RAG từ "hy vọng nó hoạt động" thành "biết nó hoạt động đến đâu".
📝 Quiz nhanh
1. Lợi thế cốt lõi của đánh giá RAG định lượng?
✅ Định lượng = chạy lại được trên cùng eval set → so sánh khách quan trước/sau thay đổi.

Chương 2 4 chỉ số cốt lõi của RAG

Đo 2 khâu: retrieval (tìm) & generation (trả lời).
Chỉ sốĐo cái gìCao =
FaithfulnessĐáp án có dựa vào context không (không bịa)Ít ảo giác
Answer RelevancyĐáp án có trúng câu hỏi khôngĐánh trúng ý
Context PrecisionContext lấy về có cái nào thừa khôngRetrieval chính xác
Context RecallLấy đủ tài liệu cần để trả lời khôngRetrieval đầy đủ
2 cặp đối xứng Context Precision/Recall đo khâu retrieval (tìm đúng tài liệu chưa). Faithfulness & Answer Relevancy đo khâu generation (LLM dùng context có tốt không). End-to-end RAG cần cả 4 tốt.

L1 · Eval Set

Chương 5 Golden Dataset

Test set cho RAG — cố định để so sánh.

Golden Dataset = tập cố định các mẫu: {question, contexts (đúng), ground_truth (answer chuẩn)}. Mỗi lần đổi RAG, chạy lại trên cùng tập → so sánh khách quan.

Tại sao "golden" Vì có đáp án chuẩn (ground truth) để đối chiếu. Không có golden set = không đo Recall/Faithfulness được. Đây là đầu việc tốn công nhưng bắt buộc.

Chương 8 Chất lượng eval set

Garbage in → đánh giá sai.
  • Đa dạng câu hỏi — factual, so sánh, đếm, lý thuyết, multi-hop.
  • Không quá dễ (AI đoán mò cũng đúng) / quá khó (tài liệu không chứa đáp án).
  • Soát lỗi — LLM có sinh câu sai/tẠo; người rà 5-10 phút.
  • Holdout — giữ 1 phần riêng, không dùng để tinh chỉnh.
📝 Quiz
1. Vì sao cần giữ holdout eval set riêng?
✅ Tinh chỉnh trên chính eval set = overfit, điểm ảo. Holdout đo khả năng tổng quát thật.

Chương 10 Chạy RAGAS

Vài dòng — nhận 4 điểm.
python · evaluate●
from ragas import evaluate
from ragas.metrics import (faithfulness, answer_relevancy,
    context_precision, context_recall)

result = evaluate(
    dataset=samples,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    llm=judge,
)
print(result)   # {'faithfulness': 0.82, 'answer_relevancy': 0.76, ...}
✍️ Bài tập 4 — Gọi evaluate
Gọi evaluate(dataset=samples, metrics=[...], llm=judge).
Xem lời giải

    dataset=samples,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    llm=judge,

Chương 12 TruLens (alternative)

Khi cần debug sâu từng bước.

TruLens tích hợp sâu hơn: instrument từng bước (retrieve → generate), vẽ trace, dashboard. Khi cần trả lời "tại sao câu này sai", TruLens cho thấy bước nào hỏng (retrieval hay generation).

Khi nào dùng TruLens Production cần giám sát liên tục, debug on-call, hoặc RAG phức tạp (multi-step agent). RAGAS đủ cho development & CI.

Chương 14 Phân tích điểm yếu

Không chỉ biết điểm — biết tại sao.

Lọc các mẫu có điểm thấp (vd Faithfulness < 0.5), đọc từng câu để tìm pattern:

  • Bịa trên chunk quá lớn (LLM lạc đề)? → thu hẹp chunk.
  • Bịa vì thiếu context? → retrieval hỏng, tăng top-k / hybrid.
  • Trả lời lac đề dù context đúng? → system prompt / đổi model.
  • Sai trên loại câu hỏi cụ thể (so sánh, multi-hop)? → thêm ví dụ / đổi chunking theo ngữ nghĩa.
20% mẫu gây 80% điểm thấp Đừng cố fix từng câu — tìm pattern. Nếu 1 loại câu hỏi luôn sai → fix systematic (chunking/prompt). Tối ưu điểm số từng câu = overfit.

Chương 15 Mẹo & cạm bẫy

Tránh sai lầm phổ biến.
  • Judge LLM cũng sai — kết hợp spot-check người (đọc 5-10 mẫu ngẫu nhiên).
  • Tốn token — Faithfulness/Relevancy gọi judge nhiều lần; giới hạn mẫu nếu budget eo hẹp.
  • Overfit eval set — giữ holdout, đánh giá định kỳ.
  • Đừng chỉ tối ưu 1 chỉ số — Faithfulness 1.0 nhưng Relevancy 0.2 = vô dụng.
  • temperature=0 cho judge — đánh giá tái lập được.
Bẫy "điểm cao nhưng user phàn nàn" Đánh giá metric ≠ trải nghiệm user. Kết hợp: metric định lượng (RAGAS) + spot-check người + log phàn nàn production. Cả 3 mới đầy đủ.

Chương 16 Dự án: eval pipeline đầy đủ

Từ eval set → CI chặn tụt điểm.
  1. Eval set: sinh 50 mẫu từ tài liệu công ty (LLM + soát lỗi tay).
  2. Config A (naive): chunk 1000, Dense top-3 → RAGAS.
  3. Cải thiện: chunking theo ngữ nghĩa + Hybrid + rerank.
  4. Config B: chạy RAGAS lại → bảng so sánh.
  5. Phân tích: lọc mẫu điểm thấp, tìm pattern, fix systematic.
  6. CI: GitHub Actions chạy RAGAS mỗi PR; tụt điểm → chặn merge.
