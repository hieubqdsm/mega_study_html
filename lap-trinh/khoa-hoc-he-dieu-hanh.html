CHƯƠNG 1 OS là gì? Vai trò & Kiến trúc máy tính

Hiểu "trùm cuối" đứng giữa phần cứng và phần mềm, và vì sao máy tính hiện đại đều theo mô hình von Neumann.

1.1. Hệ điều hành (OS) thực chất là gì?

Hãy tưởng tượng một nhà máy khổng lồ. Phần cứng (CPU, RAM, ổ đĩa, màn hình) là những cỗ máy cơ khí nằm rải rác trên sàn. Nếu mỗi công nhân (chương trình) tự chạy tới tự dùng máy, sẽ xảy ra hỗn loạn: hai người giành một máy, ai cũng muốn dùng RAM hết, máy in thì bị gởi lệnh từ chỗ khác giữa chừng. Để nhà máy chạy trơn, ta cần một quản đốc — người phân lịch, phân máy, giải quyết tranh chấp và đảm bảo mọi công việc hoàn thành đúng hạn.

Hệ điều hành (Operating System - OS) chính là vị quản đốc đó. Nó là một phần mềm đặc biệt, luôn chạy trên máy, có quyền lực cao nhất (kernel mode), đảm nhiệm hai vai trò cốt lõi: (1) quản lý tài nguyên phần cứng — chia CPU cho các chương trình, phân phối RAM, điều phối đĩa và thiết bị ngoại vi; và (2) cung cấp môi trường (abstraction) để các ứng dụng và người dùng làm việc dễ dàng hơn. Khi bạn gọi printf("Hello") trong C, bạn không hề ra lệnh trực tiếp cho card màn hình — OS nhận yêu cầu và lo phần giao tiếp phần cứng giúp bạn.

Một cách xác định khác: OS là phần mềm duy nhất luôn chạy từ lúc bật máy đến lúc tắt. Mọi chương trình khác (Chrome, Word, game...) đều do OS kích hoạt và giám sát. Các ví dụ phổ biến: Windows, macOS, Linux, Android, iOS. Bạn đang đọc tài liệu này trên một OS nào đó.

Định nghĩa chính thức Hệ điều hành là phần mềm hệ thống đóng vai trò trung gian giữa người dùng/phần mềm ứng dụng và phần cứng máy tính, quản lý tài nguyên và cung cấp các dịch vụ chung cho các chương trình.

1.2. Bốn vai trò then chốt của OS

Để dễ nhớ, các giáo trình gộp nhiệm vụ của OS thành bốn vai trò chính. Hiểu bốn vai trò này là bạn đã nắm "linh hồn" của cả môn học — vì mọi chương sau (process, memory, file, security) đều là mở rộng chi tiết của chúng.

Quản lý CPU là việc quyết định chương trình nào được dùng CPU lúc nào và bao lâu. Vì CPU chỉ có vài lõi vật lý nhưng hàng trăm tiến trình cùng "đòi" chạy, OS phải xen kẽ (interleave) chúng nhanh đến mức người dùng tưởng rằng chúng chạy đồng thời. Quản lý bộ nhớ là việc giữ cho mỗi chương trình có một vùng RAM riêng, không bị chương trình khác viết đè — nếu có đè, cả hệ thống có thể sập. Quản lý thiết bị I/O là việc giao tiếp với bàn phím, chuột, màn hình, đĩa, card mạng thông qua các driver. Quản lý file là việc biến một dãy sector thô trên đĩa thành cây thư mục có tên Documents/baitap.docx mà con người hiểu được.

1.3. Kiến trúc von Neumann — vì sao máy tính đều giống nhau

Năm 1945, nhà toán học John von Neumann đề xuất một ý tưởng đơn giản nhưng cách mạng: cả dữ liệu và chương trình (instructions) đều được lưu trong cùng một bộ nhớ. Trước đó, máy tính đầu đời như ENIAC phải được "lập trình" bằng cách cắm dây cáp thủ công — đổi chương trình là phải cắm lại dây! Von Neumann nhận ra rằng nếu lệnh cũng là dữ liệu số nhị phân, ta có thể nạp chương trình vào RAM và CPU đọc tuần tự từng lệnh, thực thi, rồi đọc lệnh tiếp theo.

Mô hình này tạo nên kiến trúc máy tính hiện đại gồm ba bộ phận: CPU (đơn vị xử lý), bộ nhớ chính (RAM) (chứa cả lệnh và dữ liệu đang dùng), và hệ thống I/O (nhập/xuất). Mọi máy tính từ điện thoại đến siêu máy tính đều theo kiến trúc này. CPU lại chia làm hai phần con: ALU (Arithmetic Logic Unit) thực hiện phép tính cộng AND OR..., và CU (Control Unit) điều phối việc nạp lệnh từ RAM.

Quá trình CPU chạy một lệnh gọi là chu kỳ lệnh (instruction cycle): Fetch (nạp lệnh từ RAM vào CPU) → Decode (giải mã xem lệnh gì) → Execute (thực thi, ví dụ cộng hai số) → Write-back (ghi kết quả về RAM/thanh ghi). Vòng lặp này lặp đi lặp lại hàng tỷ lần mỗi giây (1 GHz = 1 tỷ chu kỳ/giây).

🐍 python — Mô phỏng chu kỳ lệnh● ● ●
# Mô phỏng CPU thực thi 3 lệnh đơn giản
def fetch(memory, pc):
    return memory[pc]            # nạp lệnh tại địa chỉ pc

def execute(instr, regs):
    op, a, b = instr
    if op == 'ADD':  regs[a] += regs[b]
    elif op == 'PRINT': print(regs[a])

memory = [('ADD', 0, 1), ('PRINT', 0, 0)]   # RAM chứa lệnh + data
regs   = [5, 3]
for pc in range(len(memory)):       # chu kỳ lệnh
    instr = fetch(memory, pc)
    execute(instr, regs)            # in ra 8

1.4. CPU, Memory và I/O giao tiếp ra sao?

Ba thành phần không đứng độc lập mà nối qua một "xa lộ" dữ liệu gọi là bus hệ thống (system bus), gồm ba loại: bus địa chỉ (CPU báo muốn đọc ô nhớ số mấy), bus dữ liệu (nội dung chuyển qua lại), và bus điều khiển (tín hiệu đọc/ghi/ngắt). Khi CPU cần giá trị ở địa chỉ 0x1000, nó đặt số 0x1000 lên bus địa chỉ, phát tín hiệu READ trên bus điều khiển, rồi RAM sau vài chu kỳ nhịp sẽ đặt giá trị lên bus dữ liệu để CPU lấy.

Các thiết bị I/O (đĩa, bàn phím, card mạng) cũng gắn vào bus, nhưng chậm hơn RAM nhiều bậc. Vì sao đọc từ SSD mất micro-giây trong khi RAM chỉ mất nano-giây? Do cơ học/điện tử của chúng phức tạp hơn. Để CPU không phải "chờ rảnh", OS dùng cơ chế ngắt (interrupt): CPU ra lệnh cho đĩa đọc, rồi đi làm việc khác; khi đĩa xong, nó gửi ngắt báo "tôi xong rồi, lấy kết quả đi". Đây là nền tảng của mọi I/O hiện đại — chúng ta sẽ quay lại ở Chương 12.

Cẩn thận nhầm lẫn RAM không phải ổ đĩa. RAM mất điện là mất dữ liệu (volatile), siêu nhanh nhưng nhỏ (vài GB). Ổ đĩa (SSD/HDD) lưu lâu dài, lớn (TB) nhưng chậm hơn RAM hàng nghìn lần. OS dùng RAM làm "sân chơi" cho chương trình đang chạy và dùng đĩa để lưu lâu dài.

CHƯƠNG 2 User Mode vs Kernel Mode & System Calls

Tại sao chương trình của bạn không được phép tự ý tắt máy hay đọc file của người khác? Cùng hiểu hai "vùng quyền lực" và cổng kiểm soát duy nhất giữa chúng.

2.1. Hai chế độ: vì sao phải chia?

Hãy tưởng tượng một tòa nhà lớn có hai khu: khu văn phòng (user mode) nơi nhân viên làm việc bình thường, và phòng máy chủ (kernel mode) nơi đặt các thiết bị quan trọng — điện, mạng, dữ liệu lõi. Nhân viên không được tự ý vào phòng máy chủ, vì nếu một người vô ý bấm nhầm công tắc điện, cả tòa nhà tối thui. Khi cần điện hay dữ liệu, họ phải gửi yêu cầu qua một quầy thủ tục duy nhất, nơi bảo vệ kiểm tra xem yêu cầu hợp lệ mới thực hiện.

Trong máy tính, "phòng máy chủ" chính là kernel — phần lõi của OS có quyền truy cập toàn bộ phần cứng và bộ nhớ. "Khu văn phòng" là user mode, nơi các ứng dụng (Chrome, Word, game) chạy với quyền hạn chế: chúng không được đọc/ghi RAM tùy ý, không được truy cập trực tiếp ổ đĩa hay card mạng, không được tắt máy. Sự phân chia này bảo vệ hệ thống: nếu Chrome bị tấn công, hacker cũng chỉ có quyền của Chrome (user mode), không thể phá hoại cả kernel hay các chương trình khác.

Phần cứng CPU hỗ trợ trực tiếp cơ chế này bằng một cờ (flag) đặc biệt, thường là mode bit: 0 = kernel mode (đầy đủ quyền), 1 = user mode (hạn chế). Một số lệnh nhạy cảm (như cli tắt ngắt, hay truy cập thanh ghi điều khiển) chỉ thực hiện được khi mode bit = 0; nếu user mode cố chạy, CPU sẽ từ chối và phát ngắt lỗi.

2.2. System call — cổng giao duy nhất

Vậy ứng dụng user mode có cần đọc file không? Có. Có cần gửi data qua mạng không? Có. Vậy mà không được trực tiếp chạm phần cứng — làm sao giải quyết? Đó là lúc system call (syscall) xuất hiện: một cơ chế có kiểm soát để user mode "xin" kernel làm việc hộ. Nó giống như mẫu đơn ở quầy thủ tục: bạn điền "tôi muốn mở file /tmp/data.txt để đọc", bảo vệ (kernel) kiểm tra bạn có quyền không, nếu OK thì mở hộ và trả về một số hiệu (file descriptor) để bạn dùng sau.

Quá trình syscall diễn ra như sau. (1) Chương trình gọi một hàm thư viện như open() từ thư viện C. (2) Thư viện nạp số hiệu syscall (ví dụ 2 cho open trên Linux) vào thanh ghi và thực hiện lệnh đặc biệt syscall (x86-64) hoặc int 0x80 (x86 cũ). (3) Lệnh này khiến CPU chuyển sang kernel mode (mode bit 0) và nhảy đến một địa chỉ cố định trong kernel — syscall handler. (4) Kernel kiểm tra tham số, thực hiện thao tác phần cứng, ghi kết quả vào thanh ghi. (5) Cuối cùng kernel trả quyền lại cho user mode, chương trình tiếp tục chạy.

Mẹo nhớ System call là đường hầm an toàn duy nhất đi từ user mode sang kernel mode. Không có cách nào khác hợp lệ. Điều này cho phép OS kiểm soát hoàn toàn mọi truy cập phần cứng.
🐚 bash — Theo dõi syscall thật bằng strace● ● ●
# Xem mọi syscall mà lệnh cat sinh ra khi đọc file
$ strace cat /etc/hostname

write(1, "my-laptop\n", 10)           = 10        # ghi ra stdout

2.3. Các nhóm syscall phổ biến

Có hàng trăm syscall trên Linux, nhưng chúng rơi vào vài nhóm dễ nhớ. Nhóm quản lý tiến trình: fork (tạo tiến trình con), exec (chạy chương trình mới), exit (kết thúc), wait (đợi con). Nhóm file: open, read, write, close, lseek. Nhóm thiết bị: ioctl (điều khiển thiết bị đặc biệt). Nhóm thông tin hệ thống: getpid, gettimeofday, getuid. Nhóm truyền thông: pipe, socket, send, recv.

🇨 C — Một chương trình dùng 4 syscall kinh điển● ● ●
#include <fcntl.h>
#include <unistd.h>
int main(void) {
    char buf[100];
    int fd = open("/etc/hostname", O_RDONLY);  // syscall open
    if (fd < 0) return 1;
    int n = read(fd, buf, sizeof buf);          // syscall read
    write(1, buf, n);                          // syscall write → stdout
    close(fd);                                  // syscall close
    return 0;
}

Chương trình trên là "đặc trưng" của lập trình hệ thống: mở một tài nguyên, đọc, xử lý, rồi đóng. Quen với mẫu này, bạn đọc được hàng tá mã nguồn C trên Linux. Hàm printf mà bạn quen dùng thực ra cũng gọi write ở bên trong, sau khi đã định dạng chuỗi.

Mẹo gỡ lỗi Khi một chương trình C báo "Permission denied" hay "Bad file descriptor", hãy nhớ: đó là kernel trả lời yêu cầu syscall của bạn, không phải "lỗi của C". Dùng perror() để in thông điệp lỗi và strace để xem từng bước.

🧠 Quiz Chương 2
Câu 1. Tại sao ứng dụng phải dùng system call thay vì truy cập phần cứng trực tiếp?
Đúng. User mode (mode bit=1) không được chạm phần cứng; phải xin qua syscall để kernel (mode bit=0) thực hiện hộ, qua đó OS kiểm soát an toàn và bảo mật.

Đúng. Read là syscall: user khởi xướng, CPU nhảy sang kernel mode, kernel thực hiện I/O rồi trả kết quả và quyền lại cho user.

Đúng. Kernel có toàn quyền, nên lỗi trong kernel = lỗi cả hệ thống. Đó là lý do code kernel phải cực kỳ cẩn thận và giữ nhỏ gọn.

CHƯƠNG 3 Process (Tiến trình) & Vòng đời

Một chương trình khi được chạy trở thành "sinh vật sống" có tên, có trạng thái, có bộ nhớ — ta gọi nó là tiến trình.

3.1. Program vs Process — khác nhau ở đâu?

Một program (chương trình) là một file nằm im trên đĩa — ví dụ chrome.exe nặng 200 MB, là một loạt byte gồm mã máy và dữ liệu tĩnh. Bản thân nó không làm gì cả, chỉ nằm đó chờ được chạy. Khi bạn nháy đôi để khởi động Chrome, OS copy phần mã đó vào RAM, cấp phát một vùng nhớ riêng, tạo cấu trúc dữ liệu theo dõi, rồi bắt đầu cho CPU chạy từ lệnh đầu tiên. "Sinh vật sống" đó — program đang chạy cộng với trạng thái động — gọi là một process (tiến trình).

Một program có thể sinh ra nhiều process. Khi bạn mở hai cửa sổ Chrome, thực ra có hai (hoặc nhiều hơn) process độc lập, mỗi cái có RAM riêng, PID (process ID) riêng, nhưng cùng nguồn gốc từ file chrome.exe. Điều này quan trọng: process cô lập với nhau về bộ nhớ — Chrome cửa sổ A không đọc được RAM của cửa sổ B, đây là cơ sở của sự ổn định và bảo mật.

3.2. PCB — "hồ sơ" của mỗi tiến trình

Vì OS phải quản lý hàng trăm process cùng lúc, nó cần một "hồ sơ" cho từng cái để nhớ: tiến trình này tên gì, đang chạy ở đâu, dùng RAM vùng nào, đang đợi cái gì. Hồ sơ đó gọi là Process Control Block (PCB) — một cấu trúc dữ liệu trong kernel. Bạn có thể xem PCB là "căn cước" của process.

PCB lưu nhiều thông tin quan trọng. Process state: đang ở trạng thái nào (sẽ học ở mục sau). Program counter (PC): địa chỉ lệnh kế tiếp CPU sẽ chạy — quan trọng nhất, vì khi OS tạm dừng process để nhường CPU, nó phải nhớ chỗ dừng để tiếp tục đúng. CPU registers: giá trị các thanh ghi khi bị dừng. CPU scheduling info: độ ưu tiên, hàng đợi nào. Memory management info: bảng trang, giới hạn bộ nhớ. I/O status: danh sách file đang mở, thiết bị cấp phát.

Hình dung PCB Khi bạn đang chơi game, nhấn tổ hợp phím Ctrl+Shift+Esc để mở Task Manager, bạn thấy một dòng cho mỗi process. Dòng đó hiển thị một phần thông tin từ PCB: tên, PID, CPU%, RAM. PCB thật còn nhiều thông tin hơn nhiều — nó là "trái tim" quản lý tiến trình.

3.3. Năm trạng thái của tiến trình

Một process không phải lúc nào cũng chạy. Nó qua lại giữa các trạng thái phụ thuộc vào CPU và I/O. Mô hình 5 trạng thái kinh điển: New (vừa được tạo, OS đang khởi tạo PCB) → Ready (đã sẵn sàng, chờ được cấp CPU) → Running (đang được CPU thực thi) → Waiting/Blocked (đang đợi I/O hoặc sự kiện, tạm không thể chạy) → Terminated (đã kết thúc, OS thu hồi tài nguyên).

Chuyển trạng thái quan trọng: Ready → Running là dispatch (OS chọn process này để chạy); Running → Ready là preemption (hết thời lượng, OS giật CPU lại); Running → Waiting là khi process block (gọi syscall read, đợi đĩa); Waiting → Ready là khi I/O xong (đĩa gửi ngắt báo xong). Chú ý: process không chuyển thẳng từ Waiting sang Running — nó phải xếp hàng Ready chờ lượt.

🐍 python — Mô phỏng vòng đời tiến trình● ● ●
class Process:
    def __init__(self, pid):
        self.pid = pid
        self.state = 'new'          # 1. New
        self.pc = 0                    # program counter

    def admit(self):
        self.state = 'ready'          # 2. New → Ready

    def dispatch(self):
        assert self.state == 'ready'
        self.state = 'running'       # 3. Ready → Running

    def block(self):
        self.state = 'waiting'        # 4. Running → Waiting (gọi read)

    def io_done(self):
        self.state = 'ready'          # 5. Waiting → Ready

3.4. Context switch — đổi vỏ, tốn kém

Khi OS giật CPU từ process A sang process B, nó phải làm rất cẩn thận: nếu không lưu trạng thái A, khi quay lại A sau, A sẽ chạy tiếp sai bét. Quá trình này gọi là context switch (chuyển ngữ cảnh). Cụ thể: (1) OS (đang chạy ở kernel mode, vì ngắt hoặc syscall đã vào) lưu toàn bộ thanh ghi của A (PC, SP, các thanh ghi tổng quát) vào PCB của A. (2) OS nạp thanh ghi từ PCB của B lên CPU. (3) CPU tiếp tục chạy B đúng từ chỗ B dừng.

Context switch tốn kém: trong thời gian đó CPU không làm việc "thật" (chỉ lo dọn dẹp), RAM cache (TLB, cache L1/L2) bị xáo trộn, phải nạp lại. Một context switch mất vài micro-giây — nghe nhỏ nhưng nếu xảy ra hàng nghìn lần mỗi giây thì chi phí cộng lại đáng kể. Đây là lý do thread (Chương 4) ra đời: chuyển giữa các thread cùng process rẻ hơn nhiều vì chia sẻ bộ nhớ.

Nhầm lẫn thường gặp Context switch không phải là "lưu file đang mở". File descriptor vẫn nằm trong PCB và được giữ nguyên. Context switch chỉ lưu trạng thái CPU (thanh ghi) để CPU có thể tiếp tục đúng chỗ sau này.

CHƯƠNG 4 Thread (Luồng) & Multithreading

Process nặng nề, thread nhẹ — cùng chia sẻ bộ nhớ, chuyển đổi nhanh, mở ra thời đại đa nhân nhưng cũng mang đến những cạm bẫy mới.

4.1. Thread là gì, vì sao cần?

Một process có "bộ não" điều khiển dòng lệnh gọi là thread (luồng). Truyền thống một process chỉ có một thread, nên cùng lúc chỉ làm được một việc. Hãy tưởng tượng bạn viết một trình duyệt web chỉ có một thread: khi tải một trang nặng, toàn bộ giao diện bị "đứng" (không cuộn, không bấm nút được) cho đến khi tải xong. Khổn khổ! Cách giải quyết: cho process có nhiều thread chạy "đồng thời" — một lo tải dữ liệu, một lo vẽ giao diện, một lo chạy JavaScript.

Thread nằm bên trong process. Nhiều thread trong cùng process chia sẻ code, heap, file descriptor — chỉ riêng mỗi thread có program counter, stack (ngăn xếp lời gọi hàm) và thanh ghi riêng. Vì chia sẻ nhiều nên tạo thread rẻ hơn tạo process nhiều (không phải copy bộ nhớ), và context switch giữa các thread cùng process cũng nhanh hơn (ít thứ phải lưu, TLB không bị xáo trộn nhiều).

4.2. User thread vs Kernel thread

Có hai nơi có thể "quản lý" thread: trong user space (thư viện ứng dụng) hoặc trong kernel. User-level thread được thư viện (ví dụ GNU Portable Threads, hay coroutine của Python/Go) tạo và điều phối mà kernel không hay biết — đối với kernel, cả cụm chỉ là một thread. Ưu điểm: tạo/đổi cực nhanh, không cần syscall. Nhược điểm lớn: nếu một user thread block (gọi syscall read), toàn bộ cụm bị block, vì kernel chỉ thấy một thread và cho nó ngủ. Cũng không tận dụng được đa nhân vì kernel không phân phối các user thread cho các lõi khác nhau.

Kernel-level thread được kernel trực tiếp quản lý: mỗi thread là một đơn vị lập lịch. Ưu điểm: tận dụng được đa nhân (mỗi thread chạy trên một lõi), một thread block không kéo theo thread khác. Nhược điểm: tạo/switch chậm hơn (phải qua kernel). Hầu hết OS hiện đại (Linux, Windows) dùng mô hình 1-to-1: mỗi user thread maps một kernel thread. Linux gọi thread là task (qua clone()), và process, thread đều là task, khác nhau ở cờ chia sẻ.

Nâng cao Có cả mô hình many-to-many (M user thread maps N kernel thread, N ≤ M) cố gắng kết hợp ưu điểm cả hai — nhưng phức tạp, ít dùng. Go language dùng runtime scheduler của riêng nó (M:N) với goroutine.

4.3. Lợi ích và thách thức của multithreading

Lợi ích: (1) Responsiveness — giao diện không bị đứng khi có việc nặng chạy nền; (2) Tận dụng đa nhân — công việc tách thành nhiều thread, chạy song song trên nhiều lõi, kết thúc nhanh hơn; (3) Chia sẻ tài nguyên — các thread cùng truy cập biến chung dễ dàng, không cần IPC phức tạp; (4) Tiết kiệm — tạo thread rẻ hơn nhiều so với tạo process.

Thách thức: chia sẻ bộ nhớ là con dao hai lưỡi. Khi hai thread cùng ghi vào một biến mà không có sự phối hợp, kết quả trở nên không đoán trước — gọi là race condition (chương 6 sẽ giải quyết). Ngoài ra, deadlock (bế tắc), starvation (thread không bao giờ được chạy), khó debug (lỗi chỉ xuất hiện theo lịch nhất định) là những vấn đề nan giải mà lập trình viên đa luồng phải đối mặt.

🐍 python — Multithreading với race condition● ● ●
import threading
counter = 0

def tang():
    global counter
    for _ in range(100000):
        counter += 1     # KHÔNG AN TOÀN! nhiều thread cùng ++

threads = [threading.Thread(target=tang) for _ in range(5)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)        # Mong đợi 500000, thực tế thường nhỏ hơn!
Race condition — kẻ thù số 1 Lệnh counter += 1 không phải nguyên tử: nó đọc giá trị, cộng 1, rồi ghi lại. Nếu giữa chừng thread khác cũng đọc cùng giá trị cũ, hai thread ghi đè lên nhau → mất cập nhật. Kết quả cuối thường nhỏ hơn mong đợi. Phải dùng lock (xem Chương 6) để bảo vệ.
🇨 C — Tạo thread với pthreads● ● ●
#include <pthread.h>
#include <stdio.h>

void* work(void* arg) {
    printf("Thread %ld đang chạy\n", (long)arg);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, work, (void*)1);  // tạo thread
    pthread_create(&t2, NULL, work, (void*)2);
    pthread_join(t1, NULL);                  // đợi xong
    pthread_join(t2, NULL);
    return 0;
}

CHƯƠNG 5 CPU Scheduling (Định thời CPU)

CPU chỉ có vài lõi nhưng hàng trăm process đòi chạy — OS dùng các thuật toán thông minh để công bằng, hiệu quả và phản hồi nhanh.

5.1. Bài toán lập lịch và các tiêu chí

Khi có nhiều process ở trạng thái Ready, OS phải chọn một để chạy tiếp trên CPU. Quyết định này gọi là CPU scheduling. Bộ phận OS chuyên trách việc này là scheduler, dùng một thuật toán định thời (scheduling algorithm). Mục tiêu là tối ưu một (hoặc nhiều) chỉ số: throughput (số process hoàn thành mỗi đơn vị thời gian), turnaround time (thời gian từ lúc vào đến lúc xong), waiting time (thời gian chờ trong hàng Ready), response time (thời gian từ yêu cầu đến lần đầu được phản hồi — quan trọng với tương tác người dùng), và fairness (công bằng giữa các process).

Các thuật toán khác nhau ưu tiên các chỉ số khác nhau. Không có thuật toán "tốt nhất" tuyệt đối — chọn phụ thuộc tình huống. Hệ điều hành máy chủ ưu tiên throughput; hệ điều hành máy tính để bàn ưu tiên response time. Trước khi học thuật toán, ta cần hai khái niệm: arrival time (thời điểm process đến hàng đợi) và burst time (CPU burst — thời gian CPU process cần để chạy xong trước khi block I/O hoặc kết thúc). Burst time thực tế không biết trước, OS phải ước lượng từ quá khứ.

5.2. FCFS và SJF — đơn giản và tối ưu

First-Come First-Served (FCFS) là thuật toán đơn giản nhất: process nào đến trước được phục vụ trước, chạy đến khi xong hoặc tự block. Nó giống xếp hàng mua vé — ai đến trước đứng trước. FCFS dễ code, công bằng theo nghĩa "thứ tự đến", nhưng có nhược điểm lớn là convoy effect: nếu một process CPU-bound (cần CPU rất lâu) đến trước, các process ngắn sau phải đợi dài, làm throughput kém.

Shortest Job First (SJF) chọn process có burst time ngắn nhất trong Ready. Về lý thuyết, SJF tối ưu waiting time trung bình — không thuật toán nào (non-preemptive) làm tốt hơn. Vấn đề: ta không biết trước burst time thực! Phải ước lượng bằng exponentially weighted average (lấy trung bình có trọng số của các burst quá khứ). Một biến thể là SRTF (Shortest Remaining Time First) — preemptive: khi process mới có burst ngắn hơn phần còn lại của process đang chạy, OS giật CPU chuyển sang cái mới.

Ví dụ convoy effect Ba process: P1 (burst 24), P2 (3), P3 (3), cùng đến lúc 0. FCFS chạy P1 → P2 → P3. Waiting: P1=0, P2=24, P3=27. Trung bình = 17. Nếu chạy SJF (P2,P3,P1): waiting 0, 3, 6 → trung bình 3. SJF hơn FCFS rất nhiều!

5.3. Round Robin và Priority

Round Robin (RR) giải quyết vấn đề response time: mỗi process được chạy tối đa một time quantum (ví dụ 10ms), sau đó OS giật CPU chuyển sang process kế tiếp trong hàng đợi vòng tròn. Nếu quantum nhỏ, response time tốt (mọi process sớm được đụng CPU), nhưng context switch nhiều (overhead). Nếu quantum lớn, RR tiệm cận FCFS. Quantum 10-100ms là vùng thường dùng. RR là fair: mỗi process có đúng một quantum mỗi vòng.

Priority Scheduling gán mỗi process một độ ưu tiên, OS chọn process có priority cao nhất. Vấn đề lớn: starvation — process priority thấp có thể không bao giờ được chạy nếu luôn có process priority cao hơn xuất hiện. Giải pháp là aging: tăng dần priority của process đợi lâu, cuối cùng nó đủ cao để được chạy. Thực tế, Linux dùng Completely Fair Scheduler (CFS) kết hợp ý tưởng RR + priority + fairness một cách tinh vi.

5.4. Gantt chart — trực quan hóa lịch trình

Để so sánh các thuật toán, người ta vẽ Gantt chart — một thanh thời gian biểu diễn process nào chạy lúc nào. Giả sử 3 process đến cùng lúc 0: P1 (burst 5), P2 (burst 3), P3 (burst 1). Với SJF: P3 → P2 → P1 (chạy cái ngắn nhất trước). Gantt: |P3(0-1)|P2(1-4)|P1(4-9)|. Waiting time: P3=0, P2=1, P3=4 → trung bình (0+1+4)/3 = 1.67. Với FCFS: P1 → P2 → P3, Gantt: |P1(0-5)|P2(5-8)|P3(8-9)|, waiting: P1=0, P2=5, P3=8 → trung bình 4.33. Rõ ràng SJF tốt hơn.

Với RR (quantum=2): P1 chạy 2 (còn 3) → P2 chạy 2 (còn 1) → P3 chạy 1 (xong) → P1 chạy 2 (còn 1) → P2 chạy 1 (xong) → P1 chạy 1 (xong). Gantt: |P1(0-2)|P2(2-4)|P3(4-5)|P1(5-7)|P2(7-8)|P1(8-9)|. Response time mọi process = 0, 2, 4 → rất tốt cho tương tác, dù turnaround có thể kém hơn SJF.

🐍 python — Mô phỏng FCFS● ● ●
# FCFS: phục vụ theo thứ tự arrival, tính waiting + turnaround
processes = [('P1', 5), ('P2', 3), ('P3', 1)]   # (tên, burst)
time = 0
for name, burst in processes:
    waiting = time
    time += burst
    turnaround = time
    print(f"{name}: waiting={waiting}, turnaround={turnaround}")
# P1: waiting=0, turnaround=5
# P2: waiting=5, turnaround=8
# P3: waiting=8, turnaround=9   → TB waiting = 4.33

CHƯƠNG 6 Đồng bộ hóa & Deadlock

Khi nhiều thread cùng đụng dữ liệu chung, hỗn loạn nảy sinh. OS cung cấp công cụ phối hợp — nhưng chính công cụ đó có thể bế tắc.

6.1. Race condition — hỗn loạn dữ liệu chung

Ở Chương 4, bạn đã thấy năm thread cùng counter += 1 cho kết quả sai. Hiện tượng đó gọi là race condition (điều kiện tranh chấp): kết quả phụ thuộc vào thứ tự mà các thread xen vào nhau, mà thứ tự thì không đoán trước được. Lỗi này rất hiểm: chương trình có thể chạy đúng 999 lần rồi sai ở lần 1000, khó tái hiện, khó debug. Nguyên nhân là vì thao tác counter += 1 gồm ba bước cấp thấp: load (đọc từ RAM), add (cộng trong thanh ghi), store (ghi về RAM) — và thread khác có thể chen ngang giữa các bước.

Phần code truy cập dữ liệu chung mà ở đó race xảy ra gọi là critical section (vùng critical). Để tránh race, ta cần đảm bảo tại một thời điểm tối đa một thread ở trong critical section của cùng dữ liệu. Đây gọi là mutual exclusion (loại trừ lẫn nhau). OS cung cấp công cụ để đạt được điều đó, chủ yếu là mutex và semaphore.

Race condition thật sự nguy hiểm thế nào? Năm 2014, lỗi race trong mã nguồn iOS làm một số ứng dụng rớt ngẫu nhiên. Năm 2018, một lỗ hổng race trong Linux kernel cho phép leo thang đặc quyền (CVE-2019-8912). Đây không phải "lỗi nhỏ" — nó là một trong những nguyên nhân hàng đầu của lỗ hổng bảo mật.

6.2. Mutex — ổ khóa đơn giản

Mutex (mutual exclusion) giống ổ khóa cửa phòng: thread muốn vào critical section phải khóa (lock) trước; thread khác đến cũng cố lock sẽ bị chặn đến khi thread đầu tiên mở (unlock). Khi unlock, một trong các thread đang chờ được đánh thức và giành lock. Cơ chế này đảm bảo tại một thời điểm chỉ một thread trong critical section.

Vì sao không đơn giản dùng biến locked = True/False? Vì chính việc kiểm tra rồi gán cũng là race! Nếu hai thread cùng thấy locked=False, cả hai cùng gán True và cùng vào. Để giải, CPU cung cấp lệnh atomic đặc biệt như test-and-set hoặc compare-and-swap (CAS) — thực hiện "kiểm tra và gán" trong một bước không thể chia cắt ở mức phần cứng. Mutex được xây dựng dựa trên những lệnh này.

🇨 C — Mutex với pthreads● ● ●
#include <pthread.h>
int counter = 0;
pthread_mutex_t lock;

void* tang(void* arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);     // vào critical section
        counter++;                       // AN TOÀN
        pthread_mutex_unlock(&lock);   // rời
    }
    return NULL;
}

int main(void) {
    pthread_mutex_init(&lock, NULL);
    // ... tạo 5 thread gọi tang(), join ...
    printf("counter = %d\n", counter);  // luôn đúng 500000
}

6.3. Semaphore — đồng minh đa năng

Semaphore là khái niệm tổng quát hơn mutex, do Edsger Dijkstra đề xuất (1965). Nó là một số nguyên có hai thao tác: P (hay wait/down) giảm semaphore đi 1, nếu kết quả âm thì thread block; V (hay post/up) tăng lên 1, nếu có thread đang chờ thì đánh thức một. Khi semaphore khởi tạo bằng 1, nó hoạt động như mutex. Khi khởi tạo bằng N, nó cho phép tối đa N thread cùng vào một vùng — ví dụ giới hạn 5 kết nối database đồng thời.

Semaphore còn dùng để báo hiệu giữa thread (signaling). Ví dụ thread A sản xuất dữ liệu, thread B tiêu thụ: A gọi sem_post sau khi có data, B gọi sem_wait để chờ. Đây là mẫu producer-consumer phổ biến. Mutex chỉ khóa; semaphore vừa khóa vừa truyền tín hiệu — linh hoạt hơn nhưng cũng dễ sai hơn nếu không cẩn thận.

Phân biệt nhanh Mutex = ổ khóa, ai khóa người đó mở, dùng để bảo vệ critical section. Semaphore (giá trị N) = bộ đếm cho phép N luồng, dùng để giới hạn số truy cập hoặc truyền tín hiệu. Một binary semaphore (N=1) gần giống mutex nhưng về lý thuyết khác (ai cũng có thể post).

6.4. Deadlock — bế tắc chết người

Mutex/semaphore có thể sinh ra một vấn đề nghiêm trọng: deadlock (bế tắc). Hình dung hai người: A giữ chìa khóa phòng X, đợi chìa phòng Y; B giữ chìa phòng Y, đợi chìa phòng X. Cả hai đợi mãi, không ai nhường. Trong OS: thread T1 giữ lock L1 và chờ lock L2; thread T2 giữ lock L2 và chờ lock L1. Cả hai block vĩnh viễn.

Coffman (1971) chứng minh deadlock chỉ xảy ra khi cả 4 điều kiện cùng thoả mãn đồng thời. Phá một điều kiện bất kỳ là hết deadlock. Bốn điều kiện: (1) Mutual exclusion — tài nguyên không thể chia sẻ (một lúc một thread giữ lock). (2) Hold and wait — thread đang giữ tài nguyên A mà còn chờ B. (3) No preemption — tài nguyên chỉ giải phóng tự nguyện, không thể giật. (4) Circular wait — có chu trình chờ: T1 chờ T2 chờ ... chờ T1.

6.5. Phòng ngừa và tránh deadlock

Deadlock prevention là thiết kế sao cho ít nhất một điều kiện không bao giờ thoả. Phổ biến nhất là phá circular wait: quy ước tất cả thread phải lấy lock theo cùng thứ tự (ví dụ luôn lock L1 trước L2, không bao giờ ngược lại). Khi đó không thể tạo chu trình. Phá hold and wait bằng cách yêu cầu thread xin tất cả tài nguyên cùng lúc (atomic request). Cách này đôi khi kém hiệu quả vì phải giữ tài nguyên không cần thiết ngay.

Deadlock avoidance tinh vi hơn: OS xem xét các yêu cầu tài nguyên và từ chối nếu có nguy cơ deadlock. Thuật toán kinh điển là Banker's algorithm (Dijkstra) — giả lập ngân hàng: chỉ cấp vốn khi vẫn còn đủ "tiền" để hoàn tất mọi process. Cần biết trước tài nguyên tối đa mỗi process sẽ xin — thực tế hiếm biết được nên ít dùng trong OS thật. Thực tế, phần lớn OS (Linux/Windows) dùng deadlock detection & recovery: cho phép deadlock xảy ra, định kỳ phát hiện, kill một process để phá chu trình. Hoặc đơn giản để kẹt, người dùng tự reboot.

Quy tắc vàng Khi cần lấy nhiều lock cùng lúc, luôn lấy theo thứ tự nhất quán (ID tăng dần). Đây là cách phòng deadlock phổ biến và hiệu quả nhất trong lập trình thực tế. Một số ngôn ngữ (Rust) kiểm soát điều này ở mức compile time.

CHƯƠNG 7 Cấp phát Bộ nhớ & Paging

Từ cấp phát liền nhau (contiguous) đến phân trang (paging) — nắm vững cách OS biến một dải RAM hỗn loạn thành từng "ngăn kéo" gọn gàng cho mỗi tiến trình.

7.1. Tổng quan: OS quản lý RAM như thế nào?

Bộ nhớ chính (RAM) là tài nguyên khan hiếm và quan trọng bậc nhất của máy tính. Khi bạn mở cùng lúc trình duyệt, VS Code và Spotify, cả ba tiến trình đều "đòi" một vùng RAM để chứa mã lệnh (code), dữ liệu tĩnh (data), và stack/heap. Nhiệm vụ của OS là chia sẻ RAM sao cho (1) không có tiến trình nào ghi đè lên vùng của tiến trình khác, (2) mỗi tiến trình có cảm giác nó đang độc chiếm toàn bộ không gian địa chỉ, và (3) tốc độ truy cập vẫn nhanh nhất có thể.

Về mặt lịch sử, cách đơn giản nhất là cấp phát liền nhau (contiguous allocation): mỗi tiến trình nhận một khối RAM liên tục. Nhưng rồi người ta phát hiện ra cách này dẫn đến một "căn bệnh" nghiêm trọng tên là phân mảnh (fragmentation). Để khắc phục, OS hiện đại dùng kỹ thuật phân trang (paging) — chia bộ nhớ thành các trang nhỏ bằng nhau, cho phép các trang của một tiến trình nằm rải rác khắp RAM mà không cần liền nhau.

Trước khi đi sâu vào từng kỹ thuật, hãy nhớ quy tắc vàng: địa chỉ mà chương trình dùng (logical/virtual address) luôn khác địa chỉ vật lý thực tế trên thanh RAM (physical address). OS có một bộ phận gọi là MMU (Memory Management Unit) — nằm trong CPU hoặc chipset — chịu trách nhiệm "dịch" từ địa chỉ logic sang địa chỉ vật lý mỗi khi CPU truy cập bộ nhớ.

Đơn vị đo bộ nhớ cần thuộc lòng 1 trang (page) = thường 4 KB (4096 byte). 1 KB = 1024 byte. 1 MB = 1024 KB. 1 GB = 1024 MB. Khi gặp bài toán phân trang, luôn đổi mọi thứ ra KB để tính cho dễ.

7.2. Cấp phát liền nhau (Contiguous Allocation) & Phân mảnh

Trong sơ đồ cấp phát cũ nhất, RAM được chia thành hai phần: vùng dành cho OS (resident monitor) ở địa chỉ thấp, và vùng dành cho các tiến trình người dùng. Mỗi tiến trình được cấp một khối liền nhau. Khi tiến trình kết thúc, khối đó được giải phóng và sẵn sàng cho tiến trình mới.

Thách thức nảy sinh khi nhiều tiến trình ra-vào liên tục: lúc đầu có 3 tiến trình A, B, C chiếm lần lượt 100KB, 50KB, 80KB. Khi B kết thúc, một "lỗ" 50KB mở ra ở giữa. Nếu bây giờ tiến trình D cần 60KB, nó không thể nhét vừa vào lỗ 50KB — dù tổng RAM trống có thể vẫn còn nhiều. Đây gọi là phân mảnh ngoài (external fragmentation): bộ nhớ rải rác thành nhiều mảnh nhỏ nằm giữa các tiến trình, tổng cộng đủ lớn nhưng không liền nhau.

Ngược lại, nếu một tiến trình được cấp một khối lớn hơn chính xác nhu cầu (vì OS làm tròn lên), phần dư bên trong khối đó không dùng tới gọi là phân mảnh trong (internal fragmentation). Ví dụ: D cần 25KB nhưng OS cấp khối cố định 32KB → 7KB bên trong bị "phí".

Các chiến lược chọn "lỗ trống" khi cấp phát

Khi có nhiều khoảng trống cùng chứa được một tiến trình, OS phải chọn một. Ba chiến lược kinh điển là:

  • First-Fit: quét từ đầu, chọn lỗ đầu tiên đủ lớn. Nhanh, nhưng làm các lỗ nhỏ tụ tập ở đầu RAM.
  • Best-Fit: quét hết, chọn lỗ "vừa vặn nhất" (nhỏ nhất mà vẫn chứa được). Tiết kiệm không gian nhưng tạo ra nhiều mảnh vụn siêu nhỏ không dùng được.
  • Worst-Fit: chọn lỗ lớn nhất, hy vọng phần dư vẫn còn đủ lớn để tái sử dụng. Thực tế ít dùng vì hiệu năng kém.
Compaction — giải pháp "đắt đỏ" Để dẹp phân mảnh ngoài, OS có thể dồn (compact): dịch chuyển tất cả tiến trình về một đầu, ghép các lỗ nhỏ thành một khối lớn ở đầu kia. Nhưng compaction chỉ làm được khi tiến trình relocatable (địa chỉ phải dịch lại động), và nó rất tốn CPU — không thể chạy khi hệ thống đang tải cao.
🐍 python — Mô phỏng First-Fit● ● ●
# Danh sách các lỗ trống: (vị trí_bắt_đầu, kích_thước_kb)
holes = [(0, 100), (180, 50), (310, 80), (450, 60)]
requests = [("A", 40), ("B", 55), ("C", 30)]

def first_fit(holes, name, size):
    for i, (start, sz) in enumerate(holes):
        if sz >= size:                       # lỗ đủ lớn
            print(f"{name} -> ô @{start}, dư {sz - size} KB")
            holes[i] = (start + size, sz - size)   # cắt lỗ còn lại
            return
    print(f"{name}: KHÔNG đủ chỗ!")

for name, size in requests:
    first_fit(holes, name, size)
# A -> ô @0,    dư 60 KB
# B -> ô @310,  dư 25 KB   (ô @180 chỉ 50 < 55 nên bỏ qua)
# C -> ô @60,   dư 30 KB

7.3. Phân trang (Paging) — giải pháp cho phân mảnh ngoài

Paging chia bộ nhớ vật lý thành các khối cố định gọi là frame (khung, kích thước = kích thước trang), và chia bộ nhớ logic của tiến trình thành các khối cùng kích thước gọi là page (trang). Khi nạp một tiến trình, OS chỉ cần tìm bất kỳ frame trống nào và đặt một page vào — các page không cần liền nhau trong RAM. Nhờ vậy, không còn phân mảnh ngoài (mọi frame đều vừa đúng một page), chỉ còn phân mảnh trong nhỏ (trung bình nửa page trên mỗi tiến trình).

Để OS biết "page 3 của tiến trình X đang nằm ở frame nào", mỗi tiến trình có một cấu trúc dữ liệu gọi là page table (bảng trang). Đây là mảng một chiều: chỉ số mảng = số page, giá trị = số frame tương ứng. Mỗi khi CPU phát ra địa chỉ logic, MMU tách địa chỉ thành số page (các bit cao) và offset (độ dời bên trong page, các bit thấp), tra page table để đổi số page thành số frame, rồi ghép lại với offset để ra địa chỉ vật lý.

Công thức dịch địa chỉ (thuộc lòng!) Cho page size = 2k byte, RAM vật lý 2m byte:
• Số bit offset = k. • Số bit số trang = phần địa chỉ còn lại.
• Địa chỉ vật lý = (số frame từ page table) × (page size) + offset.
• Dịch: frame = page_table[page_number], rồi phys = (frame << k) | offset.
💻 C — Dịch địa chỉ phân trang● ● ●
#include <stdio.h>
int main(void) {
    int page_size = 4096;            // 4 KB
    // Page table của tiến trình: index = page, value = frame
    int page_table[] = {5, 9, 3, 7}; // 4 trang -> 4 frame

    unsigned int logical = 0x199C;   // 6556 decimal
    int page  = logical / page_size; // = 1
    int off   = logical % page_size; // = 2460
    int frame = page_table[page];    // = 9
    unsigned int phys = frame * page_size + off;
    printf("logical=%u -> page=%d off=%d frame=%d phys=%u\n",
           logical, page, off, frame, phys);
    // -> page=1 off=2460 frame=9 phys=39396
    return 0;
}

Kích thước trang ảnh hưởng gì?

Trang càng lớn → page table càng ngắn (ít trang), giảm chi phí truy xuất, nhưng tăng phân mảnh trong. Trang càng nhỏ → phân mảnh trong giảm, nhưng page table phình to và số lần truy cập bộ nhớ tăng. Các kiến trúc hiện đại dùng page nhiều cấp (multi-level page table) để page table không phình quá lớn khi tiến trình có không gian địa chỉ khổng lồ (64-bit).

7.4. Page Table ở đâu và TLB cứu nguy thế nào

Một vấn đề lớn: để dịch MỖI địa chỉ logic, CPU phải đọc page table nằm trong RAM — vậy là mỗi lệnh truy cập bộ nhớ biến thành hai lần truy cập RAM (lần 1: tra page table; lần 2: lấy dữ liệu thật). Tốc độ CPU bị giảm một nửa! Để giải cứu, phần cứng trang bị TLB (Translation Lookaside Buffer) — một bộ nhớ đệm (cache) nhỏ nằm trong MMU, lưu các cặp (page → frame) được dùng gần đây nhất.

Khi CPU cần dịch địa chỉ, nó tra TLB trước. Nếu hit (TLB hit): dịch luôn trong vài chu kỳ. Nếu miss (TLB miss): phải đọc page table thật từ RAM, sau đó nạp kết quả vào TLB cho lần sau. Vì tính địa phương (locality) — một tiến trình thường dùng các trang gần nhau trong thời gian ngắn — hit rate của TLB thường đạt 95-99%, khiến paging thực tế gần như không tốn thêm chi phí.

Hiệu suất TLB Effective Access Time (EAT) = hit_ratio × TLB_time + (1 − hit_ratio) × (TLB_time + 2 × memory_access).
Ví dụ TLB = 10 ns, memory = 100 ns, hit = 95%: EAT = 0.95×10 + 0.05×(10+200) = 19.5 ns. Rất gần thời gian TLB thuần — chính locality đã cứu hệ thống.

7.5. Segmentation — góc nhìn khác

Trong khi paging chia tiến trình thành các trang cùng kích thước và "vô hình" với lập trình viên, segmentation chia tiến trình thành các đoạn (segment) có ý nghĩa logic: segment code, segment data, segment stack — mỗi đoạn có kích thước khác nhau. Lập trình viên có thể nhìn thấy và tham chiếu từng đoạn. Ưu điểm: phù hợp cách tư duy của người lập trình; nhược điểm: vẫn có thể bị phân mảnh ngoài (vì đoạn có kích thước tùy ý). Nhiều OS hiện đại kết hợp cả hai thành segmentation với paging.

CHƯƠNG 8 Virtual Memory (Bộ nhớ ảo)

Bí quyết để 100 tiến trình cùng chạy dù RAM vật lý chỉ đủ cho 10 — biến đĩa cứng thành phần kéo dài của RAM.

8.1. Ý tưởng cốt lõi của Virtual Memory

Bộ nhớ ảo (Virtual Memory) là một ảo giác tuyệt đẹp do OS tạo ra: mỗi tiến trình có cảm giác nó sở hữu một không gian địa chỉ liên tục và rất lớn (vd 248 byte trên hệ 64-bit), trong khi thực tế RAM vật lý có thể nhỏ hơn nhiều. Bí quyết là OS dùng một phần đĩa cứng (gọi là swap space hoặc file phân trang) làm "kho dự phòng" — các trang chưa cần dùng được đẩy xuống đĩa, chỉ mang lên RAM khi tiến trình thực sự truy cập.

Lợi ích to lớn: bạn có thể chạy nhiều tiến trình hơn bộ nhớ vật lý cho phép, nạp các chương trình lớn hơn cả RAM, và mỗi tiến trình cô lập hoàn toàn (địa chỉ ảo của tiến trình A không bao giờ vô tình đè lên B). Đổi lại, khi dữ liệu nằm trên đĩa, truy cập chậm hơn RAM hàng ngàn lần — nên OS phải thông minh trong việc quyết định trang nào nằm đâu, trang nào đẩy xuống.

Bản chất Virtual Memory = Paging + Demand Paging + Swap. Không gian địa chỉ ảo lớn → được ánh xạ (qua page table) sang RAM vật lý hoặc swap trên đĩa. Bit valid/invalid trong mỗi entry page table cho biết trang đang ở đâu.

8.2. Demand Paging — chỉ nạp khi cần

Chiến lược phổ biến nhất là demand paging (phân trang theo yêu cầu): khi một tiến trình khởi động, OS không nạp toàn bộ các trang của nó vào RAM, mà chỉ nạp trang đầu tiên. Các trang khác nằm trên đĩa, được đánh dấu invalid trong page table (nghĩa là "chưa có trong RAM"). Khi tiến trình truy cập một trang chưa nạp, MMU phát hiện bit invalid và tạo ra một page fault — một ngoại lệ (exception) báo cho OS: "Tôi cần trang này, mang nó lên RAM đi!"

Quy trình xử lý page fault gồm 6 bước quan trọng: (1) CPU truy cập trang → MMU báo invalid; (2) CPU chuyển sang kernel mode, chạy trình xử lý page fault của OS; (3) OS kiểm tra bản đồ vùng nhớ — nếu địa chỉ hợp lệ thì đọc trang từ đĩa; (4) OS tìm một frame trống trong RAM (hoặc đẩy một trang khác xuống đĩa để giải phóng); (5) OS nạp trang từ đĩa vào frame, cập nhật page table thành valid; (6) OS trả quyền cho tiến trình, lệnh bị gián đoạn được thực thi lại (re-execute) — lần này truy cập thành công.

Page fault rất tốn kém Một page fault có thể mất ~8 ms (đọc từ SSD) đến hàng chục ms (HDD), so với ~100 ns truy cập RAM — chậm hơn 80.000 lần! Vì vậy OS phải tối ưu sao cho tỉ lệ page fault thấp nhất có thể. Nếu quá cao, hệ thống rơi vào trạng thái thảm họa là thrashing.
🐍 python — Giả lập vòng đời một trang● ● ●
# Mô phỏng đơn giản: page có thể ở RAM hoặc trên DISK
page_status = {"P0": "RAM", "P1": "DISK", "P2": "DISK"}
faults = 0

def access(page):
    global faults
    if page_status[page] == "DISK":
        print(f"⚠️  PAGE FAULT on {page} -> nạp từ đĩa...")
        page_status[page] = "RAM"
        faults += 1
    else:
        print(f"✓  {page} trúng RAM (hit)")

for p in ["P0", "P1", "P0", "P1", "P2"]:
    access(p)
print(f"Tổng page fault = {faults}")
# P0 hit, P1 FAULT, P0 hit, P1 hit, P2 FAULT -> 2 faults

8.3. Thrashing — cơn ác mộng của hệ thống

Khi OS cấp phép chạy quá nhiều tiến trình cùng lúc so với RAM, mỗi tiến trình không còn đủ frame để chứa bộ làm việc (working set — tập trang đang tích cực dùng). Kết quả: tiến trình vừa nạp trang A lên RAM để thi hành, thì ngay sau đó trang A lại bị đẩy xuống đĩa để nhường chỗ cho trang khác, rồi lại được nạp lên... vòng lặp tải/nạp không dứt. CPU dành gần như toàn bộ thời gian để xử lý page fault thay vì chạy lệnh thật — hiện tượng này gọi là thrashing.

Hiện tượng: CPU utilization thấp (do toàn bận page fault), nhưng đĩa sáng đèn liên tục (page-in/page-out không ngừng), hệ thống như "đơ cứng". Cách xử lý: giảm mức đa chương trình (degree of multiprogramming) — tạm dừng/suspend một số tiến trình để các tiến trình còn lại có đủ frame; áp dụng chiến lược working-set model hoặc page-fault frequency (PFF) để chủ động điều chỉnh.

Đừng nhầm! Thrashing KHÔNG phải là "RAM đầy". Đó là khi tổng working set của các tiến trình > dung lượng RAM. Có thể RAM vẫn còn frame trống rải rác, nhưng không đủ "cục" cho một tiến trình nào hoạt động trơn tru.

8.4. Working Set & Page-Fault Frequency

Working set W(t, Δ) của một tiến trình tại thời điểm t là tập hợp các trang được tham chiếu trong khoảng Δ tham chiếu gần nhất. Định lý do Peter Denning: nếu tổng working set của mọi tiến trình > RAM → hệ thống có xu hướng thrashing. OS nên ước lượng working set của mỗi tiến trình và đảm bảo cấp đủ frame cho nó trước khi cho tiến trình chạy.

Một cách tiếp cận khác là Page-Fault Frequency (PFF): OS theo dõi tỉ lệ page fault của mỗi tiến trình. Nếu tỉ lệ cao hơn ngưỡng trên → tiến trình đang thiếu frame, cấp thêm. Nếu thấp hơn ngưỡng dưới → tiến trình đang dư frame, thu hồi bớt để cho tiến trình khác. PFF đơn giản và hiệu quả trong thực tế.

8.5. Lợi ích, hạn chế & copy-on-write

Virtual memory cho phép: chạy chương trình lớn hơn RAM; nạp nhanh hơn (chỉ nạp trang cần); cách ly tiến trình (an toàn); hỗ trợ fork() hiệu quả nhờ copy-on-write (CoW): khi fork() tạo tiến trình con, OS không thật sự copy toàn bộ RAM của cha, mà để cha và con cùng chia sẻ các frame ở dạng read-only. Chỉ khi một bên ghi, OS mới copy trang đó ra riêng — tiết kiệm khổng lồ. Hạn chế: phức tạp cho phần cứng (cần MMU), và nếu thiết kế tồi thì thrashing phá hỏng hiệu năng.

Vì sao page size thường 4 KB? Đó là sự đánh đổi: đủ lớn để TLB cover nhiều byte (giảm miss), đủ nhỏ để phân mảnh trong thấp, và khớp với kích thước sector/block của phần cứng đĩa. Các OS hiện đại còn hỗ trợ huge pages 2 MB hoặc 1 GB cho các ứng dụng lớn (database, JVM) để giảm áp lực TLB.

CHƯƠNG 9 Thuật toán Thay thế Trang

Khi RAM đầy và một trang mới cần nạp, OS phải chọn một trang nào đó để "đá" xuống đĩa. Quyết định đó định đoạt hiệu năng — và là một trong những câu hỏi thi kinh điển nhất của môn OS.

9.1. Vấn đề & khung bài toán

Giả sử RAM có C frame và tất cả đều đang chiếm. Khi một page fault xảy ra, OS phải chọn một frame hiện tại để nạp trang mới vào, đồng thời đẩy trang cũ xuống đĩa (nếu nó bị thay đổi — dirty bit = 1). Việc chọn sai (đá một trang sẽ được dùng ngay lập tức) gây thêm page fault — cascading. Mục tiêu của thuật toán thay thế trang: giảm tối đa số page fault cho một chuỗi tham chiếu (reference string) cho trước.

Khi giải bài toán thi, mô-tip chung là: lấy chuỗi tham chiếu, mô phỏng từng bước, ghi lại khung RAM sau mỗi bước, cuối cùng đếm fault. So sánh số fault giữa các thuật toán để biết cái nào "tốt hơn" cho chuỗi đó.

Khái niệm "Belady's Anomaly" Với một số thuật toán (FIFO), khi tăng số frame, số page fault có thể tăng lên thay vì giảm — điều tưởng chừng phi lý này gọi là Belady's Anomaly. LRU và Optimal không gặp hiện tượng này (chúng thuộc lớp thuật toán "stack-based").

9.2. FIFO (First-In First-Out)

FIFO thay trang nào được nạp vào RAM sớm nhất. Cài đặt bằng một hàng đợi (queue): mỗi lần nạp trang mới, push vào cuối; mỗi lần cần thay, pop trang ở đầu. FIFO cực kỳ đơn giản, dễ cài đặt, nhưng hiệu năng kém: nó có thể đá đúng một trang vẫn đang được dùng tích cực (chỉ vì trang đó cũ).

🐍 python — FIFO● ● ●
def fifo(refs, cap):
    ram, q, faults = [], [], 0
    for p in refs:
        if p in ram:
            print(f"{p}: hit   ram={ram}"); continue
        faults += 1
        if len(ram) < cap:
            ram.append(p); q.append(p)
        else:
            old = q.pop(0)
            ram[ram.index(old)] = p
            q.append(p)
        print(f"{p}: FAULT ram={ram}")
    return faults

print("FIFO faults =", fifo([1,2,3,4,1,2,5,1,2,3,4,5], 3))

9.3. Optimal (OPT / MIN)

Optimal thay trang sẽ không được dùng trong thời gian dài nhất ở tương lai (hoặc không bao giờ dùng nữa). Về mặt lý thuyết, OPT cho số page fault ít nhất có thể — nó là chuẩn vàng để so sánh. Nhưng để chạy được OPT, OS phải biết trước toàn bộ chuỗi tham chiếu trong tương lai — điều bất khả thi ở hệ thống thật. Vì vậy OPT chỉ dùng làm mốc tham chiếu (benchmark) trong phân tích.

Cách giải OPT trong đề thi Khi cần thay, nhìn về phía trước trong chuỗi tham chiếu. Tìm trang hiện đang ở trong RAM mà lần dùng tiếp theo là xa nhất (hoặc không có → chọn ngay nó). Đá trang đó.

9.4. LRU (Least Recently Used)

LRU là phép xấp xỉ thực tế của OPT: thay trang ít được dùng gần đây nhất, dựa trên nguyên lý locality — trang ít dùng gần đây thì khả năng ít dùng sau này cũng cao. LRU cho kết quả gần với OPT và không gặp Belady's Anomaly. Tuy nhiên cài đặt LRU "chuẩn" cần phần cứng cập nhật timestamp hoặc stack mỗi lần truy cập — tốn kém. Trong thực tế, OS thường dùng xấp xỉ LRU bằng bit tham chiếu (reference bit) hoặc counter.

🐍 python — LRU bằng danh sách có thứ tự● ● ●
def lru(refs, cap):
    ram, faults = [], 0      # ram[-1] là mới dùng nhất
    for p in refs:
        if p in ram:
            ram.remove(p); ram.append(p)   # đẩy lên cuối (mới dùng nhất)
            continue
        faults += 1
        if len(ram) < cap:
            ram.append(p)
        else:
            ram.pop(0); ram.append(p)      # đá ít dùng nhất (đầu ds)
    return faults
print("LRU faults =", lru([1,2,3,4,1,2,5,1,2,3,4,5], 3))

9.5. Clock / Second-Chance

Clock (còn gọi Second-Chance) là xấp xỉ LRU rẻ tiền: mỗi frame có một bit tham chiếu (reference/use bit), ban đầu = 1 khi được nạp hoặc truy cập. Khi cần thay, OS quét các frame theo vòng tròn (như kim đồng hồ): nếu frame có bit = 1 → reset thành 0 và bỏ qua (cho nó "cơ hội thứ hai"); nếu bit = 0 → thay frame đó. Nhờ đó, các trang được dùng tích cực (luôn có bit = 1) ít bị đá; trang ít dùng (bit đã bị reset về 0) sẽ bị thay. Clock cho hiệu năng gần LRU nhưng cài đặt rẻ.

CHƯƠNG 10 File & Directory (Hệ thống File)

Đĩa cứng chỉ là một dải sector vô danh. Hệ thống file (file system) biến nó thành những "tài liệu" có tên, có thư mục, có ý nghĩa — thứ mà con người và ứng dụng có thể hiểu được.

10.1. File là gì? Thuộc tính và các thao tác

Một file (tập tin) là một tập hợp thông tin có liên quan, được lưu trên thiết bị lưu trữ thứ cấp (đĩa, SSD), được hệ điều hành quản lý như một đơn vị logic. Với người dùng, file là thứ "nhấp đôi để mở" — văn bản, ảnh, video, mã nguồn. Với OS, file là một chuỗi byte (hoặc block) có tên, có vị trí vật lý trên đĩa, và một bộ siêu dữ liệu (metadata) mô tả nó.

Mỗi file có các thuộc tính (attributes / metadata) không nằm trong nội dung file nhưng do OS lưu kèm: tên file, phần mở rộng, kích thước (byte), ngày tạo/sửa cuối, chủ sở hữu, quyền truy cập (permissions), vị trí vật lý trên đĩa. Trên Linux, các thuộc tính này nằm trong cấu trúc inode; trên Windows là MFT entry.

Hầu hết OS cung cấp 6 thao tác nguyên thủy qua system call: create (tạo file rỗng), open (mở để truy cập, OS trả về một "file descriptor" / "file handle"), read/write (đọc/ghi từ vị trí con trỏ hiện tại), seek (dịch con trỏ vị trí), close (đóng, giải phóng tài nguyên), và delete (xóa). 10.2. Cấu trúc thư mục (Directory Structures)

Một directory (thư mục) về mặt kỹ thuật là một dạng file đặc biệt — nội dung của nó là danh sách các entry, mỗi entry ánh xạ một tên tới một file/thư mục con. Vai trò chính của thư mục là tổ chức file để con người dễ tìm, và cung cấp không gian tên (namespace) để hai file cùng tên ở hai thư mục khác nhau không xung đột.

Theo thời gian, cấu trúc thư mục đã tiến hóa qua các mô hình sau:

  • Single-level (1 cấp): toàn bộ file nằm trong một thư mục duy nhất. Đơn giản, không khả thi khi có nhiều file (trùng tên).
  • Two-level (2 cấp): mỗi người dùng có một thư mục riêng (vd FMS trên các hệ cũ). Tách người dùng nhưng vẫn khó tổ chức bên trong.
  • Tree (cây): thư mục lồng nhau tạo thành cây, gốc là / (Linux) hoặc C:\ (Windows). Mỗi file có đường dẫn (path) duy nhất. Là mô hình phổ biến nhất.
  • Acyclic-Graph (đồ thị không chu trình): cho phép một file xuất hiện ở nhiều thư mục qua link (hard link, symbolic link). Linh hoạt hơn nhưng phức tạp quản lý.
  • General graph (đồ thị tổng quát): cho phép cả chu trình — hiếm gặp do khó duyệt và dễ gây rác.

10.3. Đường dẫn (Path) — tuyệt đối và tương đối

Trong cấu trúc cây, mỗi file được định danh bằng một đường dẫn (path). Có hai loại: tuyệt đối (absolute) — bắt đầu từ gốc, vd /home/alice/report.pdf; và tương đối (relative) — tính từ thư mục đang làm việc (current working directory), vd ../photos/cat.jpg. OS luôn lưu đường dẫn tuyệt đối nội bộ; đường dẫn tương đối chỉ là tiện ích cho người dùng.

Hai ký tự đặc biệt dùng trong path: . (thư mục hiện tại) và .. (thư mục cha). Để chuyển thư mục, dùng system call chdir(); để biết thư mục hiện tại, dùng getcwd(). Khi phân giải path, OS đi từng cấp thư mục, đọc directory entry, tìm inode/entry của cấp tiếp theo, cho tới khi tới file đích.

Hard link vs Symbolic link Hard link: một entry thư mục trỏ trực tiếp tới cùng inode → hai "tên" chia sẻ một file thật; xóa một tên chưa xóa dữ liệu (inode sống tới khi ref count = 0). Symbolic (soft) link: một file đặc biệt chứa đường dẫn tới file khác → trỏ "tên", nếu file đích bị xóa thì link "gãy" (broken). Hard link không đi chéo filesystem; symlink thì có.

10.4. Mounting & FS layout tổng quan

Một hệ thống có thể có nhiều filesystem (phân vùng khác nhau, ổ đĩa khác nhau, USB). Để truy cập thống nhất, OS dùng thao tác mount: gắn cây thư mục của một filesystem vào một thư mục đã có (gọi là mount point) trong cây chính. Sau khi mount, người dùng thấy nội dung của filesystem con như thể nó nằm trong thư mục đó. Lệnh mount trên Linux, hoặc tự động mount khi cắm USB trên Windows.

Trên đĩa, một filesystem có các vùng layout điển hình: boot block (chương trình nạp lúc bật máy), superblock (thông tin tổng quan: loại FS, số block, vị trí inode tự do), inode table (mô tả file), data blocks (chứa nội dung file), và free-space management (theo dõi block còn trống — sẽ học ở chương 11).

CHƯƠNG 11 Cấp phát & Quản lý không gian đĩa

Một file dài 1 GB gồm hàng triệu block — OS lưu chúng trên đĩa như thế nào để vừa nhanh, vừa tiết kiệm, vừa dễ mở rộng? Đó là câu hỏi mà ba phương pháp cấp phát dưới đây trả lời.

11.1. Cấp phát liền nhau (Contiguous Allocation)

Giống contiguous allocation trong RAM: mỗi file chiếm một dải block liên tục trên đĩa. Cấu trúc directory chỉ cần lưu 2 giá trị cho mỗi file: (block_bắt_đầu, số_lượng_block). Ưu điểm: truy cập tuần tự lẫn ngẫu nhiên đều rất nhanh (đĩa chỉ seek một lần, rồi đọc liên tục); đơn giản. Đây là phương pháp dùng cho CD-ROM, DVD và một số định dạng media cố định.

Nhược điểm chí mạng: phân mảnh ngoài khi file được tạo-xóa nhiều lần, và vấn đề kích thước file không biết trước — nếu file tăng dần theo thời gian, OS không có chỗ để mở rộng (block kề đã bị file khác chiếm), buộc phải compact hoặc từ chối ghi. Vì vậy contiguous hiếm được dùng cho filesystem đa năng.

Bài toán "kích thước không biết trước" Nhiều ứng dụng (log, database, tải file) tạo file tăng dần. Với contiguous, OS phải đoán trước kích thước cuối; đoán thấp → phải di chuyển cả file (chậm); đoán cao → lãng phí. Đây là lý do FS đa năng bỏ qua phương pháp này.

11.2. Cấp phát liên kết (Linked Allocation)

Linked allocation giải quyết triệt để vấn đề mở rộng: mỗi file là một danh sách liên kết các block — mỗi block chứa dữ liệu lẫn con trỏ tới block tiếp theo. Directory chỉ cần lưu (block_đầu); muốn đọc tuần tự thì đi theo con trỏ; muốn thêm thì lấy một block trống bất kỳ, móc vào cuối. Không có phân mảnh ngoài, không lo kích thước file.

Trade-off: truy cập ngẫu nhiên chậm — để đọc byte ở block thứ 500 phải đi qua 499 con trỏ. Hơn nữa con trỏ chiếm vài byte dữ liệu của mỗi block (giảm hiệu quả) và nếu một block hỏng (bad sector) thì toàn bộ phần sau của file bị mất (chuỗi đứt). Một biến thể cải tiến là FAT (File Allocation Table) — đưa tất cả con trỏ vào một bảng riêng ở đầu phân vùng, vừa cache được vừa không tốn byte dữ liệu (dùng cho exFAT, MS-DOS).

🐍 python — Minh hoạ Linked Allocation● ● ●
# File "song.mp3" -> directory lưu: start=12
# Chuỗi block trên đĩa:
#   block 12  -> next 47
#   block 47  -> next 88
#   block 88  -> next 5
#   block  5  -> next None  (hết file)

linked = {12: 47, 47: 88, 88: 5, 5: None}
def read_all(start):
    cur, out = start, []
    while cur is not None:
        out.append(cur)
        cur = linked[cur]
    return out

print(read_all(12))   # [12, 47, 88, 5]

11.3. Cấp phát chỉ mục (Indexed Allocation) & I-node

Indexed Allocation gom tất cả con trỏ của file vào một block chỉ mục (index block): directory lưu con trỏ tới index block; index block chứa mảng các con trỏ tới data block thật. Ưu điểm lớn: truy cập ngẫu nhiên nhanh (đọc index block → tra vị trí block thứ i → đọc luôn), không phân mảnh ngoài, dễ mở rộng. Nhược điểm: tốn 1 index block cho mỗi file (lãng phí với file rất nhỏ), và file rất lớn thì 1 index block không đủ → cần cấp chỉ mục nhiều cấp (multi-level index) hoặc chained index.

I-node (Index-node) — trái tim của Unix FS Mỗi file có một inode: một cấu trúc chứa metadata + một mảng con trỏ tới data block. Inode của ext2/ext3 có 12 direct pointer, 1 single indirect, 1 double indirect, 1 triple indirect. Thiết kế này cho phép: file nhỏ (≤ 12 block) truy cập siêu nhanh (direct), file vừa dùng single indirect, file khổng lồ (lên tới hàng TB) dùng double/triple indirect — một sự cân bằng tuyệt vời.

11.4. Quản lý không gian trống (Free Space Management)

Song song với việc cấp phát cho file, OS phải theo dõi không gian đĩa còn trống để biết block nào có thể cấp cho file mới. Hai phương pháp phổ biến:

  • Bitmap (Bit vector): mỗi block tương ứng 1 bit — 0 = trống, 1 = đã dùng. Đơn giản, dễ tìm block trống liên tiếp (để contiguous), kích thước nhỏ (1 TB đĩa / 4 KB block ≈ 32 MB bitmap). Dùng bởi ext2/ext3, NTFS…
  • Linked list (danh sách liên kết các block trống): các block trống được móc vào nhau; mỗi block còn lưu số lượng block trống kế tiếp. Tiết kiệm dung lượng khi đĩa gần đầy, nhưng khó tìm dải liên tiếp.

Một số FS kết hợp cả hai: bitmap trong RAM để tra nhanh, đồng thời danh sách nhóm (block group / cylinder group) để tối ưu vị trí vật lý (đặt file gần nhau trên cùng cylinder để giảm seek).

🐍 python — Bitmap: tìm block trống● ● ●
# bitmap[i] = 0 -> block i trống; 1 -> đã dùng
bitmap = [0]*16
# Giả sử file A chiếm 3 block bắt đầu từ 2
for i in range(2, 5): bitmap[i] = 1
# file B chiếm 2 block
for i in range(10, 12): bitmap[i] = 1

def alloc(n):
    for start in range(len(bitmap) - n + 1):
        if all(bitmap[k] == 0 for k in range(start, start + n)):
            for k in range(start, start + n): bitmap[k] = 1
            return start
    return -1   # hết chỗ

print("Cấp 3 block -> start =", alloc(3))   # -> 0
print("Cấp 2 block -> start =", alloc(2))   # -> 5
Mẹo thi Khi gặp bài "cho bitmap X, cấp n block", nhớ tìm dải liên tiếp đủ dài với contiguous; với linked/indexed chỉ cần đếm tổng số bit 0 ≥ n. Đừng nhầm!

11.5. Tổng kết & so sánh các FS thực tế

Trong đời thực, các filesystem kết hợp nhiều ý tưởng trên: ext4 (Linux) dùng indexed allocation với inode + extents + bitmap; NTFS (Windows) dùng MFT (Master File Table) lưu attribute chứa danh sách extent; FAT/exFAT dùng linked allocation thông qua bảng FAT; ZFS/Btrfs dùng copy-on-write + checksum + B-tree cho độ tin cậy cao. Hiểu nguyên lý ở chương này giúp bạn đọc được cách các FS "thực" tối ưu.

Chương 12 I/O: Polling, Interrupts & DMA

Cách CPU giao tiếp với thiết bị ngoại vi — từ hỏi vòng (polling), ngắt (interrupt) đến truy cập bộ nhớ trực tiếp (DMA).

12.1 Thiết bị I/O và mô hình giao tiếp với CPU

Một máy tính không chỉ có CPU và RAM — nó còn có bàn phím, màn hình, ổ đĩa, card mạng, USB, loa… Tất cả đều là thiết bị I/O (Input/Output). Vấn đề cốt lõi: CPU cực nhanh (vài GHz), còn thiết bị I/O cực chậm (bàn phím vài lần/giây, ổ cứng vài trăm MB/giây). Làm sao để hai bên "nói chuyện" được với nhau mà CPU không phải ngồi chờ?

Mỗi thiết bị I/O được điều khiển bởi một chip gọi là device controller (bộ điều khiển thiết bị). Ví dụ: controller của ổ đĩa, controller của bàn phím, controller USB. Controller này có sẵn một vài thanh ghi (register) mà CPU có thể đọc/ghi:

  • Data register — chứa dữ liệu thực sự (byte gõ từ bàn phím, byte ghi ra ổ đĩa).
  • Status register — báo tình trạng thiết bị: READY (sẵn sàng), BUSY (đang bận), ERROR (lỗi)…
  • Control register — CPU ghi lệnh vào đây để điều khiển thiết bị (ví dụ "bắt đầu đọc sector số 42").

Để CPU truy cập các thanh ghi này, có hai mô hình phần cứng:

Mô hìnhCách hoạt độngVí dụ
Memory-Mapped I/OCác thanh ghi của thiết bị được "ghép" vào không gian địa chỉ bộ nhớ. CPU dùng lệnh mov, load, store bình thường để đọc/ghi.ARM, MIPS, hầu hết CPU hiện đại
Port-Mapped I/O (I/O ports)Có một không gian cổng riêng, CPU dùng lệnh đặc biệt IN / OUT để truy cập.x86 (Intel/AMD)

12.2 Polling — CPU tự hỏi vòng

Cách đơn giản nhất để CPU nhận dữ liệu từ thiết bị là Polling (Programmed I/O): CPU liên tục đọc status register trong một vòng lặp, chờ đến khi bit READY = 1, thì mới đọc data register.

📄 polling.c — đọc byte từ thiết bị bằng polling●●●
// Giả lập memory-mapped I/O: con trỏ trỏ tới thanh ghi thiết bị
volatile unsigned char *STATUS = (unsigned char*)0x40000000;
volatile unsigned char *DATA   = (unsigned char*)0x40000001;
#define READY_BIT 0x01

char read_device(void) {
    // Vòng lặp polling: chờ tới khi bit READY = 1
    while ((*STATUS & READY_BIT) == 0) {
        // CPU "kẹt" ở đây — gọi là busy-waiting (chờ bận rộn)
    }
    return (char) *DATA;   // thiết bị đã sẵn sàng, đọc dữ liệu
}

Ưu điểm của polling: phần cứng cực kỳ đơn giản, không cần mạch ngắt; dễ hiểu, dễ lập trình. Nhược điểm chí mạng: CPU bị "đốt" 100% thời gian chỉ để kiểm tra một bit, không làm việc khác được. Nếu thiết bị chậm (bàn phím), CPU lãng phí hàng triệu chu kỳ chỉ để chờ một lần gõ phím. Từ khóa volatile rất quan trọng ở đây: nó báo compiler đừng tối ưu việc đọc STATUS ra khỏi vòng lặp (vì giá trị có thể thay đổi do phần cứng).

Khi nào dùng polling?Polling hợp lý khi thiết bị khá nhanh và có thể đoán trước (ví dụ đọc sector đĩa khi đã định vị xong đầu đọc), hoặc trong hệ thống nhúng đơn giản không cần đa nhiệm. Trong OS đa nhiệm hiện đại, polling thuần túy hiếm khi dùng cho thiết bị chậm vì nó "đóng băng" toàn bộ hệ thống.

12.3 Interrupts (Ngắt) — thiết bị chủ động báo

Thay vì CPU phải đi hỏi vòng, interrupt đảo ngược vai trò: CPU ra lệnh cho thiết bị rồi đi làm việc khác; khi thiết bị xong việc, nó gửi một tín hiệu phần cứng gọi là interrupt request (IRQ) lên CPU. CPU ngắt công việc hiện tại, nhảy đến một hàm đặc biệt gọi là Interrupt Service Routine (ISR) để xử lý, rồi quay lại công việc cũ như chưa hề xảy ra gì.

Quy trình xử lý ngắt gồm các bước:

  1. Thiết bị kéo đường IRQ lên (hoặc xuống) → CPU nhận được ngắt.
  2. CPU lưu ngữ cảnh (các thanh ghi, Program Counter, flags) vào stack.
  3. CPU tra Interrupt Vector Table (IVT) — một bảng địa chỉ — để tìm địa chỉ ISR tương ứng với IRQ đó.
  4. CPU nhảy đến ISR và thực thi. ISR phải ngắn gọn và nhanh.
  5. Khi ISR kết thúc, CPU thực hiện lệnh iret (interrupt return), phục hồi ngữ cảnh, quay về chương trình bị ngắt.
⚙️ button_irq.c — đăng ký ISR trong Linux kernel (C thật)●●●
#include <linux/module.h>
#include <linux/interrupt.h>
#include <linux/gpio.h>

// ISR — chạy trong ngữ cảnh ngắt, phải nhanh, KHÔNG được sleep!
static irqreturn_t button_isr(int irq, void *dev_id) {
    printk(KERN_INFO "Ngat! Nut bam tren GPIO17 duoc nhan\n");
    return IRQ_HANDLED;   // bao da xu ly xong ngat nay
}

static int __init my_init(void) {
    // Xin cap phat duong ngat cho chan GPIO17, canh len (RISING)
    return request_irq(gpio_to_irq(17), button_isr,
                       IRQF_TRIGGER_RISING, "my_button", NULL);
}

static void __exit my_exit(void) {
    free_irq(gpio_to_irq(17), NULL);   // giai phong duong ngat
}
module_init(my_init);
module_exit(my_exit);

Vì ISR chạy trong ngữ cảnh ngắt (tức là đang "gián đoạn" một tiến trình khác), nó không được phép sleep, không được phân bổ bộ nhớ, không được dùng lock có thể block. Do đó Linux chia xử lý ngắt làm hai phần:

  • Top-half (chính là ISR): làm tối thiểu — nhận dữ liệu, xác nhận ngắt (ACK) với thiết bị, rồi lên lịch bottom-half.
  • Bottom-half (workqueue, softirq, tasklet): phần xử lý nặng (xử lý dữ liệu, đánh thức tiến trình) được hoãn lại, chạy sau trong ngữ cảnh an toàn hơn.
Tưởng tượng đời thườngPolling giống bạn cứ 5 giây lại mở cửa xem shipper đến chưa. Interrupt giống shipper bấm chuông khi đến — bạn cứ làm việc, nghe chuông mới ra nhận. Rõ ràng interrupt tiết kiệm công sức hơn rất nhiều!

12.4 DMA (Direct Memory Access) — chuyển dữ liệu "bỏ qua" CPU

Kể cả với interrupt, vẫn còn một vấn đề: khi ổ đĩa đọc được 1 sector (512 byte hay 4 KB), nếu CPU phải tự copy từng byte từ thiết bị vào RAM thì nó vẫn mất rất nhiều chu kỳ. Giải pháp là DMA (Direct Memory Access): một chip riêng gọi là DMA controller đảm nhận việc copy dữ liệu giữa thiết bị và RAM, CPU chỉ cần "giao việc" rồi đi chỗ khác chơi.

Quy trình DMA:

  1. CPU ghi vào các thanh ghi của DMA controller: địa chỉ RAM đích, số byte cần chép, số hiệu thiết bị, hướng chuyển.
  2. CPU ra lệnh "bắt đầu" rồi lập tức đi thực thi tiến trình khác.
  3. DMA controller điều phối đường bus, chuyển dữ liệu thẳng thiết bị ↔ RAM không qua CPU.
  4. Trong lúc chuyển, DMA có thể "ăn cắp" chu kỳ bus" (cycle stealing) hoặc chuyển nguyên một burst (loạt) — tạm thời CPU không truy cập được RAM.
  5. Khi xong, DMA controller gửi một interrupt cho CPU báo "đã chép xong N byte". CPU lúc này mới vào xử lý.

13.1 Vì sao cần bảo mật? Bộ ba CIA & nguyên tắc đặc quyền tối thiểu

Hệ điều hành là người quản lý mọi tài nguyên (CPU, RAM, file, thiết bị) của máy tính. Nếu không có bảo mật, một chương trình bất kỳ có thể đọc mật khẩu của bạn, xóa file hệ thống, hay ghi đè lên RAM của chương trình khác. OS phải đảm bảo rằng mỗi chương trình chỉ làm đúng những gì nó được phép. Mục tiêu bảo mật thường tóm gọn trong ba chữ CIA:

  • C — Confidentiality (Bảo mật): thông tin chỉ được đọc bởi người được phép. Ví dụ: file /etc/shadow chỉ root đọc được.
  • I — Integrity (Toàn vẹn): thông tin không bị sửa đổi trái phép. Ví dụ: hacker không thể thay đổi điểm thi trong CSDL.
  • A — Availability (Khả dụng): hệ thống vẫn phục vụ người dùng hợp lệ. Ví dụ: chống tấn công DoS làm sập server.
Nguyên tắc đặc quyền tối thiểu (Least Privilege)Mỗi tiến trình, mỗi người dùng chỉ nên có đủ quyền để làm việc của mình, không hơn. Trình duyệt web không cần quyền xóa file hệ thống; chương trình tính toán không cần quyền mở cổng mạng. Nếu bị hack, thiệt hại bị giới hạn ở mức tối thiểu.

Trong Linux, sau khi bạn đăng nhập (authentication), quyền của bạn được đại diện bởi một số nguyên là UID (User ID) và GID (Group ID). Mỗi file mang nhãn chủ sở hữu, nhóm, và 9 bit quyền (rwx cho user/group/other). OS dùng UID để authorization: kiểm tra xem bạn có được đọc/ghi/thực thi file hay không.

int check_password(const char *input, const char *stored_hash) {

    if (result == NULL) return 0;

}

OS dùng mô hình trừu tượng gọi là Access Matrix để mô tả quyền. Hàng là các domain (miền bảo vệ — thường là user/process), cột là các object (file, thiết bị, tiến trình), mỗi ô chứa tập hợp các quyền (read, write, execute…).

Vì ma trận thường rất thưa (phần lớn ô trống), OS không lưu nguyên ma trận mà triển khai theo một trong hai hướng:

  • ACL (Access Control List) — lưu theo cột: mỗi object mang một danh sách (user → quyền). Ví dụ: ls -l hiển thị ACL rút gọn của Linux. Dễ hỏi "ai được truy cập file này?".
  • Capability (C-list) — lưu theo hàng: mỗi domain mang một danh sách "thẻ bài" (capability) chỉ ra object + quyền mà nó được dùng. Dễ hỏi "tôi được làm gì?". Ví dụ: file descriptor trong Unix chính là một dạng capability.
Mẹo nhớACL gắn với object (file biết ai được dùng nó). Capability gắn với subject (tiến trình mang theo thẻ bài để chứng minh quyền). Linux dùng ACL (permission bits). File descriptor là capability.

13.4 Protection Rings — bảo vệ bằng phần cứng

Để buộc các chương trình tuân thủ quyền, CPU x86 cung cấp protection rings (vòng bảo vệ) — các cấp đặc quyền phần cứng:

RingAi chạy ở đâyQuyền
Ring 0Kernel (nhân hệ điều hành)Toàn quyền: truy cập phần cứng, RAM, I/O, lệnh đặc quyền
Ring 1/2(hiếm dùng) — driver, dịch vụ hệ thốngHạn chế hơn Ring 0
Ring 3Ứng dụng người dùng (user mode)Bị giới hạn: không được dùng lệnh đặc quyền

Khi một chương trình ở Ring 3 muốn làm việc cần đặc quyền (đọc file, gửi gói mạng), nó phải thực hiện system call — lệnh đặc biệt (syscall / int 0x80 / sysenter) khiến CPU chuyển từ Ring 3 lên Ring 0 một cách có kiểm soát, vào kernel xử lý rồi quay về. Đây chính là ranh giới User Mode ↔ Kernel Mode đã học ở Chương 2.

Vì sao virus khó "phá" trực tiếp kernel?Vì phần cứng ép mọi ứng dụng vào Ring 3. Muốn can thiệp kernel, mã độc phải tìm lỗ hổng leo thang đặc quyền (privilege escalation) để leo từ Ring 3 lên Ring 0 — đó là lý do kernel bug cực kỳ nguy hiểm và được vá gấp.

OS hiện đại trang bị nhiều lớp phòng thủ phần cứng/phần mềm:

  • ASLR (Address Space Layout Randomization): random hóa địa chỉ của code/stack/heap để hacker không đoán được vị trí để nhảy tới.
  • DEP / NX bit (Data Execution Prevention): đánh dấu vùng RAM chứa dữ liệu là "không được thực thi", chặn shellcode trong stack/buffer.
  • Sandboxing: chạy tiến trình không tin cậy trong môi trường cô lập (chroot, container, seccomp), giới hạn syscall.
  • SELinux / AppArmor: MAC (Mandatory Access Control) — chính sách bảo mật do hệ thống áp, ngay cả root cũng bị ràng buộc.
Bảo mật là chuỗi yếu nhấtOS có thể hoàn hảo, nhưng nếu người dùng chạy file lạ hoặc dùng mật khẩu yếu, toàn bộ hệ thống sụp đổ. Bảo mật = phần cứng + OS + ứng dụng + con người. Phòng thủ theo "nguyên lý chiều sâu" (defense in depth): nhiều lớp chồng nhau.

DEP/NX đánh dấu vùng dữ liệu (stack, heap) là "non-executable", chặn shellcode. ASLR thì randomize địa chỉ — một lớp khác.

14.2 fork() — tạo tiến trình con

System call fork() tạo ra một bản sao của tiến trình đang gọi (gọi là tiến trình cha), bản sao đó là tiến trình con. Con có bản sao gần như giống hệt cha: cùng code, cùng biến (copy-on-write), chỉ khác fork() trả về giá trị khác nhau cho hai bên.

Giá trị trả về của fork()Ý nghĩa
> 0 (PID của con)Cha nhận được
== 0Con nhận được
== -1Lỗi (thường do quá nhiều tiến trình)
🌱 fork_demo.c — fork cơ bản (C thật)●●●
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("Truoc fork, PID=%d\n", getpid());

    pid_t pid = fork();          // tạo tiến trình con

    if (pid == 0) {
        // Nhánh CON (fork trả về 0)
        printf("Day la CON, PID=%d, cha=%d\n", getpid(), getppid());
    } else if (pid > 0) {
        // Nhánh CHA (fork trả về PID của con)
        printf("Day la CHA, PID=%d, con=%d\n", getpid(), pid);
    } else {
        perror("fork that bai");
    }
    return 0;
}
Copy-on-Write (CoW)fork() không thật sự copy toàn bộ RAM (rất tốn). Thay vào đó, cha và con chia sẻ các trang vật lý, đánh dấu "chỉ đọc". Chỉ khi một bên ghi, kernel mới copy riêng trang đó. Vì thế fork() cực nhanh và ít tốn RAM.

14.3 exec() — thay thế chương trình đang chạy

Sau khi fork, tiến trình con là "bản sao" cha — thường ta không muốn vậy. Ta muốn con chạy một chương trình khác. System call họ exec giúp việc đó: nó thay toàn bộ image (code + data + stack) của tiến trình hiện tại bằng một chương trình mới, giữ nguyên PID. Nếu thành công, exec không bao giờ trả về (vì code cũ đã bị xóa).

14.4 wait() & waitpid() — cha chờ con kết thúc

Khi tiến trình con kết thúc, nó không biến mất ngay mà trở thành zombie (xem 14.5) cho đến khi cha "thu dọn". System call wait() (hoặc waitpid()) cho phép cha chờ con kết thúc và thu thập mã thoát của con.

⏳ wait_demo.c — chờ con và đọc exit status●●●
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();
    if (pid == 0) {
        printf("Con lam viec...\n");
        sleep(2);
        exit(42);              // mã thoát = 42
    }
    int status;
    waitpid(pid, &status, 0);   // cha block tới khi con xong
    if (WIFEXITED(status))
        printf("Con thoat voi ma %d\n", WEXITSTATUS(status)); // in 42
    return 0;
}

WIFEXITED(status) trả về true nếu con thoát bình thường (gọi exit hoặc return); khi đó WEXITSTATUS(status) cho mã thoát (chỉ 0–255). Nếu con bị giết bởi tín hiệu (SIGKILL…), dùng WIFSIGNALED / WTERMSIG.

Chương 15 Thread & Đồng bộ hóa với pthreads

pthread_create, mutex, semaphore trong C — và giải bài toán kinh điển producer–consumer.

15.1 Tạo thread với pthread_create

Nhắc lại: process có bộ nhớ riêng, còn thread (luồng) trong cùng process chia sẻ code, heap, và biến toàn cục — chỉ có stack riêng. Nhờ chia sẻ, việc giao tiếp giữa các thread rất dễ (cùng trỏ tới biến chung) nhưng cũng sinh ra vấn đề race condition. Trên Linux, ta dùng thư viện POSIX threads (pthread), compile với cờ -pthread.

🧵 thread_demo.c — tạo 2 thread chạy song song●●●
#include <stdio.h>
#include <pthread.h>

void* say_hello(void* arg) {
    long id = (long) arg;       // nhận đối số (ép từ void*)
    for (int i = 0; i < 3; i++)
        printf("Thread %ld: xin chao!\n", id);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, say_hello, (void*)1);  // tạo thread 1
    pthread_create(&t2, NULL, say_hello, (void*)2);  // tạo thread 2

    pthread_join(t1, NULL);   // chờ thread 1 xong
    pthread_join(t2, NULL);   // chờ thread 2 xong
    return 0;
}
// Biên dịch: gcc thread_demo.c -o demo -pthread

Đối số truyền vào thread là void* — ta hay "nhét" số nguyên hoặc con trỏ cấu trúc vào. pthread_join chặn (block) cho đến khi thread kết thúc, tương tự wait với process. Nếu quên join mà main return, toàn bộ process (cùng các thread) bị thu dọn.

15.2 Race condition — khi "chia sẻ" thành tai họa

Giả sử 2 thread cùng tăng một biến chung counter 100 000 lần. Kết quả mong đợi là 200 000, nhưng thực tế thường nhỏ hơn và thay đổi mỗi lần chạy! Lý do: thao tác counter++ không nguyên tử — nó gồm 3 bước: đọc → cộng → ghi. Nếu hai thread xen ngang nhau, một lần tăng bị "mất".

⚡ race.c — BUG: đua điều kiện trên counter chung●●●
#include <stdio.h>
#include <pthread.h>

int counter = 0;   // biến CHUNG cho mọi thread

void* worker(void* arg) {
    for (int i = 0; i < 100000; i++)
        counter++;        // KHÔNG an toàn! read-modify-write
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d (mong doi 200000)\n", counter);
    return 0;
}
Bug khó tái hiệnRace condition thường không làm chương trình crash ngay mà cho kết quả "lúc đúng lúc sai" — cực kỳ khó debug. Đây là lý do đồng bộ hóa là chủ đề trung tâm của lập trình đa luồng.

15.3 Mutex — khóa đoạn găng (critical section)

Mutex (mutual exclusion) là một "khóa". Trước khi truy cập biến chung, thread gọi pthread_mutex_lock; khi xong thì pthread_mutex_unlock. Khoảng giữa hai lệnh đó gọi là critical section (đoạn găng) — chỉ một thread được vào cùng lúc, các thread khác phải chờ.

🔒 mutex.c — SỬA race bằng mutex●●●
#include <stdio.h>
#include <pthread.h>

int counter = 0;
pthread_mutex_t lock;          // khai báo mutex

void* worker(void* arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);     // vào đoạn găng
        counter++;                       // an toàn!
        pthread_mutex_unlock(&lock);   // rời đoạn găng
    }
    return NULL;
}

int main(void) {
    pthread_mutex_init(&lock, NULL);
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);  // luôn ra 200000
    pthread_mutex_destroy(&lock);
    return 0;
}

Mutex giải quyết được race, nhưng khóa/mở nhiều lần quanh một lệnh đơn là kém hiệu quả (overhead). Với thao tác đếm đơn giản ta có thể dùng thao tác nguyên tử (__sync_fetch_and_add hoặc C11 <stdatomic.h>); mutex phù hợp khi cần bảo vệ nhiều thao tác phức tạp trên một cấu trúc dữ liệu.

15.4 Semaphore & bài toán Producer–Consumer

Semaphore (tín hiệu) là bộ đếm nguyên tử với hai thao tác: sem_wait (P — giảm, nếu =0 thì chờ) và sem_post (V — tăng, đánh thức người chờ). Semaphore không chỉ "loại trừ" như mutex mà còn dùng để đếm tài nguyên và báo hiệu giữa các thread.

Ứng dụng kinh điển là Producer–Consumer: một thread sản xuất dữ liệu bỏ vào buffer, thread khác tiêu thụ. Cần ba semaphore/lock: empty (số ô trống), full (số ô có dữ liệu), và một mutex bảo vệ buffer.

🔄 prodcons.c — producer/consumer dùng semaphore●●●
#include <stdio.h>
#include <pthread.h>
#include <semaphore.h>

#define N 5                       // kích thước buffer
int buf[N], in = 0, out = 0;
sem_t empty, full;
pthread_mutex_t m;

void* producer(void* a) {
    for (int i = 0; i < 10; i++) {
        sem_wait(&empty);            // chờ có ô trống
        pthread_mutex_lock(&m);
        buf[in] = i; in = (in+1) % N;  // thêm vào buffer vòng
        printf("San xuat %d\n", i);
        pthread_mutex_unlock(&m);
        sem_post(&full);             // tăng số ô có dữ liệu
    }
    return NULL;
}

void* consumer(void* a) {
    for (int i = 0; i < 10; i++) {
        sem_wait(&full);             // chờ có dữ liệu
        pthread_mutex_lock(&m);
        int item = buf[out]; out = (out+1) % N;
        printf("  Tieu thu %d\n", item);
        pthread_mutex_unlock(&m);
        sem_post(&empty);            // tăng số ô trống
    }
    return NULL;
}

int main(void) {
    sem_init(&empty, 0, N);       // ban đầu N ô trống
    sem_init(&full,  0, 0);       // 0 ô có dữ liệu
    pthread_mutex_init(&m, NULL);
    pthread_t p, c;
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}
Thứ tự rất quan trọngProducer phải sem_wait(&empty) TRƯỚC khi lock mutex. Nếu khóa mutex trước rồi mới chờ empty, trong khi consumer cũng đang giữ mutex chờ full → deadlock! Quy tắc: semaphore đếm luôn được chờ ngoài mutex.

15.5 Deadlock đa luồng & cách phòng

Với nhiều mutex, dễ rơi vào deadlock: thread A giữ lock1 chờ lock2, thread B giữ lock2 chờ lock1 — cả hai chờ mãi mãi. Bốn điều kiện Coffman (mutual exclusion, hold-and-wait, no preemption, circular wait) đã học ở Chương 6 vẫn áp dụng. Cách phòng phổ biến nhất: luôn khóa theo cùng thứ tự (lock ordering) để phá điều kiện "circular wait".

Mẹo tránh deadlock(1) Khóa nhiều mutex theo một thứ tự cố định toàn cục. (2) Dùng pthread_mutex_timedlock để không chờ vô hạn. (3) Giữ đoạn găng ngắn nhất có thể. (4) Tránh gọi lại hàm chưa biết trong khi đang giữ lock.
🧠 Quiz Chương 15
1. Các thread trong cùng process chia sẻ gì?
Thread cùng process chia sẻ code, heap, biến toàn cục — chỉ stack (biến cục bộ) là riêng. Đây là lý do truy cập biến chung sinh race condition.
2. Trong producer–consumer, tại sao phải sem_wait(&empty) trước khi lock mutex?
Nếu producer giữ mutex rồi chờ empty, consumer cũng cần mutex để tiêu thụ (giải phóng ô) → cả hai kẹt = deadlock. Semaphore đếm phải chờ ngoài mutex.
3. Mutex được dùng chủ yếu để?
Mutex = mutual exclusion, bảo vệ đoạn găng (critical section) để chỉ một thread vào cùng lúc, loại bỏ race condition.

Chương 16 IPC: Pipes, Shared Memory, Message Queues

Các cơ chế giao tiếp giữa tiến trình: pipe(), FIFO, shmget/shmat, msgsnd/msgrcv — và so sánh khi nào dùng cái nào.

16.1 Vì sao cần IPC?

Mỗi process có không gian địa chỉ riêng, cách ly hoàn toàn (process A không thể đọc RAM của process B). Điều này an toàn nhưng tạo ra vấn đề: làm sao các tiến trình "nói chuyện" được với nhau? — ví dụ shell pipe ls | grep, hay trình duyệt gửi yêu cầu tới server. IPC (Inter-Process Communication) là tập hợp các cơ chế OS cung cấp để tiến trình trao đổi dữ liệu. Các cơ chế chính: Pipe, FIFO, Message Queue, Shared Memory, Socket, Signal.

16.2 Pipe — ống dẫn vô danh và có tên (FIFO)

Pipe là một kênh byte một chiều: một đầu ghi, một đầu đọc, dữ liệu theo thứ tự FIFO. Unnamed pipe (tạo bằng pipe(fd)) chỉ dùng được giữa các process có quan hệ cha–con (vì pipe được kế thừa qua fork). Named pipe (FIFO) tạo bằng mkfifo là một file đặc biệt trên đĩa, bất kỳ process nào cũng mở được.

🪈 pipe.c — cha ghi, con đọc qua unnamed pipe●●●
#include <stdio.h>
#include <string.h>
#include <unistd.h>

int main(void) {
    int fd[2];                 // fd[0]=đọc, fd[1]=ghi
    pipe(fd);

    pid_t pid = fork();
    if (pid == 0) {            // CON: đọc
        close(fd[1]);            // đóng đầu ghi (con không cần)
        char msg[100];
        int n = read(fd[0], msg, sizeof msg);
        msg[n] = '\0';
        printf("Con nhan: %s", msg);
    } else {                   // CHA: ghi
        close(fd[0]);            // đóng đầu đọc
        write(fd[1], "Xin chao tu cha!\n", 19);
    }
    return 0;
}
Luôn đóng đầu không dùngNếu con muốn đọc mà không đóng fd[1], read sẽ không bao giờ trả về EOF (vì vẫn còn một đầu ghi mở — chính con). Đóng đầu không dùng là thói quen bắt buộc khi làm việc với pipe.

Named pipe (FIFO) thì khác — nó tồn tại như một file trên đĩa, hai process hoàn toàn độc lập cũng giao tiếp được:

📂 fifo — hai terminal bất kỳ giao tiếp●●●
# Terminal 1: tạo FIFO (chỉ làm 1 lần)
mkfifo /tmp/myfifo

# Terminal 1: ghi (block cho tới khi có ai mở đọc)
echo "hello" > /tmp/myfifo

# Terminal 2 (chạy song song): đọc
cat /tmp/myfifo

16.3 Shared Memory — chia sẻ RAM tốc độ cao

Shared memory là cơ chế IPC nhanh nhất: kernel ánh xạ một vùng RAM vật lý vào không gian địa chỉ của nhiều process cùng lúc. Các process đọc/ghi vùng đó như bộ nhớ thường — không có copy qua kernel. Nhược điểm: phải tự đồng bộ (vì nhiều process ghi cùng lúc = race), thường kết hợp với semaphore.

💾 shm.c — System V shared memory (C thật)●●●
#include <stdio.h>
#include <sys/ipc.h>
#include <sys/shm.h>
#include <string.h>

int main(void) {
    key_t key = ftok("shm.c", 65);            // tạo khóa
    int shmid = shmget(key, 1024, 0666|IPC_CREAT); // cấp phát 1KB
    char *str = (char*) shmat(shmid, NULL, 0);     // attach vào process

    printf("Ghi du lieu vao shared memory...\n");
    strcpy(str, "Hello tu shared memory!");

    shmdt(str);                                  // detach
    // shmctl(shmid, IPC_RMID, NULL);  // xóa khi không cần nữa
    return 0;
}

Một process khác gọi cùng ftok + shmget + shmat sẽ thấy đúng chuỗi "Hello tu shared memory!" — vì hai process trỏ tới cùng vùng RAM vật lý. Đây là nền tảng của nhiều cơ chế hiệu năng cao (X11 shared memory, database shared buffer…).

16.4 Message Queue — gửi/nhận "tin nhắn" có cấu trúc

Message queue là một hàng đợi trong kernel chứa các "tin nhắn". Mỗi tin nhắn có một type (kiểu) để phân biệt, receiver có thể chọn nhận theo type. Khác pipe (luồng byte vô định danh), message queue giữ ranh giới tin nhắn — gửi 3 lần 100 byte, bên kia nhận được 3 tin nhắn 100 byte chứ không trộn lẫn.

📨 msgq.c — gửi/nhận tin nhắn qua System V queue●●●
#include <stdio.h>
#include <sys/ipc.h>
#include <sys/msg.h>

struct msgbuf {
    long mtype;              // kiểu tin nhắn (bắt buộc là long đầu tiên)
    char mtext[100];         // nội dung
};

int main(void) {
    key_t key = ftok("msgq.c", 66);
    int qid = msgget(key, 0666|IPC_CREAT);

    struct msgbuf msg;
    msg.mtype = 1;                          // gán type
    sprintf(msg.mtext, "Tin nhan %d", 42);
    msgsnd(qid, &msg, sizeof msg.mtext, 0);   // gửi

    struct msgbuf rcv;
    msgrcv(qid, &rcv, sizeof rcv.mtext, 1, 0);    // nhận type=1
    printf("Nhan: %s\n", rcv.mtext);

    msgctl(qid, IPC_RMID, NULL);              // xóa queue
    return 0;
}

🧠 Quiz Chương 16
1. Unnamed pipe (pipe()) có hạn chế gì?
Unnamed pipe được kế thừa qua fork, nên chỉ dùng giữa cha–con (hoặc anh em). Để các process độc lập giao tiếp, dùng FIFO (named pipe) hoặc các cơ chế khác.
2. Cơ chế IPC nào nhanh nhất và tại sao?
Shared Memory ánh xạ cùng RAM vật lý cho nhiều process → truy cập trực tiếp, không copy. Đổi lại phải tự đồng bộ bằng semaphore/mutex.
3. Khác biệt chính giữa pipe và message queue về ranh giới dữ liệu?
Pipe = byte stream (ghi 3 lần có thể bị gộp khi đọc). Message queue giữ nguyên từng tin nhắn, kèm type để nhận chọn lọc.
